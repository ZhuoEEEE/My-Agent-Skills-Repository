# embedded-workspace-init 使用说明

## 1. 文档用途

本文面向使用 `embedded-workspace-init` Skill 的用户，说明它解决什么问题、如何发起请求、哪些操作会写入磁盘、什么时候需要确认，以及初始化完成后如何使用嵌入式 Agent 工作区。

本仓库中与该 Skill 有关的内容分为两部分：

- `embedded-workspace-init/`：设计、优化方案和本文档所在的描述目录。
- `built-skills/embedded-workspace-init/`：实际可安装、可验证的 Skill 内容，包括 `SKILL.md`、脚本、运行规则、模板和 schema。

本文是 Skill 自身的使用说明，不等同于实际工作区初始化后生成的根 `USER_GUIDE.md`。后者用于日常开发；本文重点说明如何调用 Skill 完成初始化、迁移、刷新或受控升级。

## 2. Skill 解决的问题

`embedded-workspace-init` 为 Windows 上的嵌入式或 MCU 产品建立一个独立、纯净的 Agent 工作区，同时保留用户原有 IDE 工程作为用户权威工程。

核心目标是：

- 用户继续在原目录、原 IDE 和原编辑器中维护权威工程。
- Agent 不在用户权威工程中直接进行日常开发，而是在独立工作副本中修改、构建和验证。
- Agent 工作区与用户权威工程的真实路径互不包含。
- 单 MCU、多 MCU、多个分散工程目录和多个并行任务使用同一套模型。
- Agent 修改只有在用户明确表达“发布到用户工程”的意图后才会写回。
- 同步使用可取回的 Git 基线、三方比较、逐文件哈希、恢复快照和原子替换，避免目录镜像覆盖。
- 工作区规则、状态、工具、证据、恢复数据和项目知识有明确位置，不污染根目录。

它提供的是由副本、Git、哈希、路径检查和恢复快照组成的软隔离，不是操作系统账户、ACL、虚拟机或安全沙箱级别的绝对隔离。

## 3. 适用与不适用场景

### 3.1 应使用本 Skill 的场景

- 从一个或多个现有嵌入式工程创建新的 Agent 工作区。
- 为全新的嵌入式产品创建空的纯净 Agent 工作区。
- 将非空的旧 Agent 工作区迁移到新的纯净目录。
- 在已初始化工作区中重新扫描源、目标或构建事实。
- 增加新的用户权威源组或 Agent 自建源组。
- 调整已有源组的目录映射。
- 导入参考工程、创建可修改的参考副本或将参考工程提升为正式开发源。
- 对现有工作区执行规则、结构、映射、policy 或 schema 的受控升级。

### 3.2 不应使用本 Skill 的场景

- 普通固件功能开发、修复缺陷或日常代码审查。
- 仅构建、测试或发布一个已经正常工作的日常任务，除非需要修复工作区配置本身。
- 自动安装或升级 IDE、编译器、SDK、Pack、许可证或其他依赖。
- 把现有工程转换成 CMake、PlatformIO 或其他构建体系。
- 自动修改业务源码以通过初始化或构建。
- 初始化阶段烧录、擦除、调试、复位或操作板卡。
- 在用户工程内部创建 Agent 管理目录。
- 扫描整台电脑来猜测工程位置。

初始化完成后的普通开发由工作区根 `AGENTS.md` 和 `workspace-management/` 中的受管脚本约束，不需要每次再次调用本 Skill。

## 4. 使用前准备

### 4.1 环境要求

当前实现的运行边界是：

- Windows 本地主机。
- 本地文件系统路径。
- PowerShell 7（`pwsh`）。
- Git。
- Codex `Local` 环境。

当前版本不承诺以下场景的一致性：

- 网络共享目录。
- WSL 路径与 Windows 路径混合访问。
- 跨主机并发操作同一工作区。
- 使用 Codex-managed 或 permanent worktree 作为 Agent 管理根。

### 4.2 需要准备的信息

首次调用前，尽量准备：

- 希望创建的 Agent 工作区路径。
- 一个或多个用户权威工程的实际路径。
- 如果工程目录分散，哪些目录必须保持共同的相对拓扑。
- 是否存在旧 Agent 工作区；若存在，提供旧路径和新的空目标路径。
- 是否只要求检查，不允许任何写入。
- 是否有参考工程需要导入，以及它的路径或固定 Git revision。
- 多个相似 MCU 工程中，哪些属于正式目标、示例、备份或历史副本。

所有 IDE 和编辑器中的文件应先保存到磁盘。Skill 只能检查已保存内容，无法读取或保护尚未保存的缓冲区。

### 4.3 路径要求

Agent 工作区必须与每个用户权威工程满足：

- 两者都是可解析、可读的本地真实路径。
- Agent 工作区不位于用户工程内部。
- 用户工程不位于 Agent 工作区内部。
- 符号链接、junction、大小写别名或映射不会造成间接包含。
- 用户工程不能直接充当 `sources/<source-id>/integration/`。

首次初始化的目标目录应为空。非空目录会进入只读迁移规划流程，而不会被直接认领或覆盖。

## 5. 如何调用

该 Skill 配置为仅显式调用，必须在请求中写出 `$embedded-workspace-init`。普通对话不会自动触发它。

### 5.1 从现有工程初始化

```text
$embedded-workspace-init 使用以下用户工程初始化一个外部纯净 Agent 工作区：
- Agent 工作区：D:\AgentWorkspaces\motor-controller
- 用户工程：D:\Firmware\motor-controller
保持原有 IDE 工程结构不变。先检查路径、源组和映射；需要确认时先给出完整计划。
```

如果当前打开的目录就是用户工程，Skill 不会在其中创建管理文件。它只会盘点并要求选择一个外部空目录。

### 5.2 创建没有用户权威源的新工作区

```text
$embedded-workspace-init 在 D:\AgentWorkspaces\new-device 创建纯净嵌入式 Agent 工作区。
目前没有用户权威工程，后续源码由 Agent 创建。
```

这种源使用 `agent-created`，不虚构用户路径，也没有导入或发布关系。

### 5.3 只读检查

```text
$embedded-workspace-init 只读检查 D:\AgentWorkspaces\motor-controller 的状态、路径、Git 边界和目标登记情况。不要创建或修改任何文件、目录、日志、Git 对象或构建输出。
```

“只读”“只检查”“不要更新状态”等表达具有最高优先级。此模式下不会生成计划文件，也不会为了记录检查结果而写日志。

### 5.4 迁移旧工作区

```text
$embedded-workspace-init 检查旧工作区 D:\OldAgent\motor 和新的空目录 D:\AgentWorkspaces\motor-v2，制定迁移计划。确认前零写入，旧目录必须保持原样。
```

第一次调用只会输出完整迁移计划和批准摘要。只有在用户明确批准未变化的完整计划后，才会应用迁移。部分确认不会触发部分迁移；Skill 会先生成删减后的新计划并再次等待确认。

### 5.5 刷新已有工作区

```text
$embedded-workspace-init 重新扫描当前工作区，登记新增 MCU 工程并保留所有已确认字段。只执行事实刷新；如果涉及结构、映射、policy 或 schema 变化，先给出升级计划。
```

事实刷新应保持幂等：不重复创建目标、不改写已确认值、不递增未变化的映射版本，也不创建空 Git 提交。

### 5.6 增加外部源

```text
$embedded-workspace-init 将 D:\Firmware\sensor-node 作为新的用户权威源加入当前工作区。先展示 source-id、目录映射、过滤项、Git 边界和导入计划。
```

若多个分散目录需要维持共同依赖关系，应在请求中说明。Skill 可以把多个路径作为一个源组的多个可逆映射，而不是复制一个包含大量无关内容的共同父目录。

### 5.7 导入参考工程

本地参考工程：

```text
$embedded-workspace-init 将 D:\References\vendor-demo 导入为参考工程，reference-id 使用 vendor-demo，仅供 Agent 查阅，不作为开发或发布目标。
```

Git 参考工程：

```text
$embedded-workspace-init 将 https://example.com/vendor/demo.git 的固定 revision <commit-or-tag> 导入为参考工程，说明用途、适用目标和许可证状态。
```

参考工程正文保持只读。需要试改或构建时，应创建当前 workstream 下的 reference copy；需要成为正式源码时，必须明确要求“提升为正式开发源”。

### 5.8 升级工作区规则或结构

```text
$embedded-workspace-init 更新当前工作区约束，先只读审计并展示 policy/schema 版本、文件操作、Git 影响、验证和回滚计划。确认前不要写入。
```

规则升级始终采用两阶段流程。第一次调用只规划；用户批准后再次核对状态。只要路径、文件哈希、Git 状态或计划摘要发生实质变化，原批准即失效。

## 6. 首次初始化会发生什么

### 6.1 空目录且信息明确

对明确指定的空目录，显式调用授权创建固定工作区骨架。典型流程是：

1. 解析 Agent 工作区和用户源的真实路径。
2. 检查路径包含关系、链接、已知多活工作区和外层 worktree。
3. 确认源组、可逆映射、过滤项和稳定 ID。
4. 以 `workspace_state: initializing` 创建工作区。
5. 创建 Agent 管理 Git。
6. 为每个受支持源组创建独立私有 Git 和集成副本。
7. 导入已保存、允许纳管且不敏感的内容。
8. 创建可取回的用户同步基线和文件索引。
9. 发现候选 MCU 目标和构建配置，但不覆盖用户已确认事实。
10. 验证路径、schema、固定目录、规则文件、映射、Git 边界和用户源未被写入。
11. 只有全部必要不变量通过后，才原子切换为 `workspace_state: active`。

源代码本身不能构建并不必然代表初始化失败。布局和状态可以正确激活，同时把构建结果记录为失败、不可用或未验证。

### 6.2 非空目录、旧工作区或不明确内容

此时第一次调用只进行只读盘点。计划应包含：

- 旧路径和新路径的真实值。
- 用户源及源组定义。
- 旧相对路径到新相对路径的复制映射。
- 排除项、敏感项和未解决项。
- Agent 管理 Git、源组私有 Git、用户 Git 的边界。
- 旧规则文件的归档方式。
- 验证、失败处理和回滚方式。
- 绑定计划内容的批准摘要。

批准后会重新盘点。源文件在复制过程中发生变化时，新工作区保持 `initializing`，旧目录仍保持原样，不会交换、移动、重命名或删除。

## 7. 初始化后的目录与职责

典型根目录如下：

```text
<workspace>/
|-- AGENTS.md
|-- README.md
|-- USER_GUIDE.md
|-- project-docs/
|-- reference-projects/
|-- sources/
|-- work/
`-- workspace-management/
```

- `AGENTS.md`：唯一生效的工作区级 Agent 规则。
- `README.md`：一屏式入口和目录概览。
- `USER_GUIDE.md`：初始化后面向用户的日常使用手册。
- `project-docs/`：经确认的产品、方案、路线、决策和版本资料。
- `reference-projects/`：不可变参考工程包装和正文。
- `sources/<source-id>/integration/`：源组集成副本和用户同步基线聚合点，不是日常编辑目录。
- `work/<workstream-id>/`：每个逻辑任务的独立工作副本、任务状态、证据和产物。
- `workspace-management/`：配置、schema、指南、工具、索引、同步状态、事务、证据和恢复数据。

固定骨架和职责 README 在初始化时创建。项目知识正文、参考实例、workstream、日志、证据、恢复快照和迁移记录只在对应操作实际发生时创建。

## 8. 初始化后的正确入口

初始化完成后：

1. 在 Codex 中只打开 Agent 工作区真实根目录。
2. 使用 `Local` 环境。
3. 不为这个根目录创建 Codex-managed 或 permanent worktree。
4. 不把用户工程、`sources/*/integration/`、`work/*/sources/*/` 或参考正文单独添加为 Codex 项目。
5. 普通任务直接用自然语言描述，不必再次调用 `$embedded-workspace-init`。

这样可以确保根 `AGENTS.md` 是唯一有效规则，并且本机配置、源组私有 Git、同步状态和工作副本都处于同一管理根下。

## 9. 三种工程位置

### 9.1 用户权威工程

用户继续在原 IDE 中维护的原始工程。它位于 Agent 工作区之外，默认只读。只有以下两类流程可写入：

- 用户明确要求把某个 workstream 发布回用户工程。
- 用户单独授权启用或操作用户 Git。

### 9.2 集成副本

位于 `sources/<source-id>/integration/`，由源组私有 Git 管理。它用于导入用户已保存内容、保留用户同步基线和汇总状态，不用于普通任务直接编辑。

### 9.3 Workstream 副本

位于 `work/<workstream-id>/sources/<source-id>/`。正常修改、生成、构建和测试都在这里执行。不同任务使用不同 linked worktree，减少并行任务互相污染。

## 10. 三套 Git

### 10.1 Agent 管理 Git

工作区根 `.git` 只跟踪规则、说明、可移植配置、schema、工具、模板、项目知识、迁移历史和 workstream 元数据。它不代表源码状态。

### 10.2 源组私有 Git

每个源组拥有独立、无推送目的地的私有 Git。它保存用户同步基线、workstream 分支、linked worktree 和内部检查点。私有提交不会写入用户 Git。

### 10.3 用户工程 Git

用户 Git 是可选的。初始化工作区不会自动创建、提交或推送用户 Git。没有 Git 时，可在初始化之后单独要求启用；现有 Git 会被识别和保护。

根目录的 `git status` 只显示管理元数据。查看源码修改时，必须检查相应 workstream 或源组私有仓库。

## 11. 日常任务如何运行

新逻辑任务默认创建新 workstream。只有明确说“继续某个 workstream”且能唯一识别时，才复用已有任务。

常见表达：

```text
实现电机堵转保护，并构建 motor-controller 的 debug 配置。
继续 20260910-motor-stall-a13f。
查看当前活动和未解决的 workstream。
把我的工程最新修改导入 Agent 工作区。
把当前 workstream 的修改同步回我的工程。
```

Workstream 会记录：

- 任务目标和状态。
- 涉及的源组与读写范围。
- 用户同步基线、任务起点和冻结结果提交。
- 固定到具体提交的依赖 workstream。
- 未解决修改和交接摘要。

当两个活动任务的写入范围重叠，或生成器、链接脚本、IDE 元数据等影响范围较大时，Agent 应先报告冲突并协调所有权。

## 12. 目标与构建配置

一个源组可包含多个 MCU 目标；一个目标可包含多个稳定 `build-id`，例如 `debug`、`release` 或板级变体。目标 ID 和 build ID 不应因为目录名称大小写或 IDE 显示名称变化而随意改变。

有歧义时同时指定两者：

```text
构建 target-id 为 motor-controller、build-id 为 release 的配置。
```

构建命令使用工具 ID、参数数组和相对工作目录登记。普通构建只能在 Agent 副本中执行。对用户工程的构建只能作为已经冻结且文件验证通过的发布事务的一部分运行。

初始化不会为了获得绿色构建而安装工具、清理用户缓存、重新生成源码或修复业务代码。构建成功必须同时具有期望 ELF、HEX、BIN 等产物证据，不能只依据退出码为零。

## 13. 导入、发布与基线

### 13.1 方向

- `inspect`：只读比较，不写入。
- `import`：用户权威工程 -> 集成副本/当前 workstream。
- `publish`：冻结 workstream -> 用户权威工程。

只说“同步”且方向不明确时，Agent 应询问一次。明确说“把当前任务写回我的工程”时，应直接进入发布流程，而不是再要求固定口令。

### 13.2 三类基线

- 用户同步基线：用户工程与 Agent 私有副本最后一次内容一致的可取回提交。
- 任务基线：workstream 的 `task_base_commit`，决定任务自身发布差异的起点。
- 构建基线：某个 target/build-id 最近一次实际构建成功的提交和证据。

从未成功构建过的工程仍可进行三方同步。构建基线不能代替用户同步基线。

### 13.3 发布前条件

发布前应：

1. 明确当前 workstream。
2. 保存 IDE 和编辑器缓冲区。
3. 确认映射版本、用户同步基线、任务基线和依赖仍有效。
4. 冻结 `head_commit`。
5. 对所有涉及源完成扫描、三方比较、范围检查和完整 dry run。
6. 生成逐文件清单及摘要。
7. 经用户确认该清单后才应用。

发布只包含 `task_base_commit..head_commit` 和已固定依赖的提交闭包，不会夹带其他 workstream 的新提交。

### 13.4 写入和恢复

应用前会为所有受影响路径建立恢复快照并记录 SHA-256。每个文件写入前再次核对当前哈希：

- 新增文件必须仍不存在。
- 修改或删除文件必须仍等于计划中的用户版本。
- 新内容使用同目录临时文件和原子替换。
- 删除会先把原文件移入恢复区。
- 不使用目录镜像、隐式删除、时间戳覆盖、`/MIR` 或 `--delete`。

冲突应在写入前停止。应用或文件验证失败时，只有能证明现场仍等于事务预期结果才自动回滚；否则进入 `recovery_required`，阻止新的导入和发布。

### 13.5 发布后构建失败

如果文件已经正确发布，但用户工程构建失败：

- 已发布文件、恢复快照和日志会保留。
- 用户选择“保留”时，只推进用户同步基线，不更新成功构建基线。
- 用户选择“回滚”时，系统重新检查哈希后恢复。
- 不能安全证明回滚条件时，不覆盖外部修改，而是进入人工恢复状态。

## 14. 参考工程

参考工程位于：

```text
reference-projects/<reference-id>/
|-- README.md
|-- manifest.json
`-- project/
```

它保留来源、固定版本、许可证、用途、适用目标、已知差异和文件哈希。参考正文不会自动成为源组、目标或发布对象。

需要修改或构建时，创建：

```text
work/<workstream-id>/reference-copies/<reference-id>/project/
```

该副本拥有独立临时私有 Git，并记录来源和清理条件。只有在 workstream 已终止且需要的成果已保留后才清理。

明确要求提升参考工程时，它会成为 `reference-promoted` 源组，但仍然没有用户发布路径。若要以后发布到某个外部目录，必须再单独批准权威映射。

## 15. 项目知识

跨任务长期事实位于 `project-docs/`：

- `PRODUCT.md`：长期产品目标、用户、场景和能力边界。
- `SOLUTION.md`：当前有效的系统划分和约束。
- `ROADMAP.md`：阶段目标、依赖、范围、退出条件和下一步。
- `decisions/`：已确认、推迟或被替代的跨任务决策。
- `versions/`：版本目标、纳入/排除范围和完成标准。

初始化不会创建空的 PRODUCT、SOLUTION 或 ROADMAP 正文。任务中的候选结论先留在 workstream；只有用户确认其跨任务有效后才提升为项目事实。

## 16. 敏感文件与复杂 Git 拓扑

导入会保留许可证、版权声明、启动代码、链接脚本和必要二进制依赖，同时排除或阻止：

- `.git` 元数据。
- IDE 本机工作区状态，例如 Eclipse `.metadata`。
- 已确认可重建的缓存和构建产物。
- 私钥、令牌、生产签名材料、许可证激活秘密和设备数据转储。

高熵二进制本身不等于秘密。名称含 `license` 的文件也可能是法律声明；无法可靠分类时会列为待确认项，而不是静默删除或复制。

发现 submodule、嵌套 Git、已有 linked worktree 或 Git LFS 时，受影响源组会暂停。Skill 不会复制 `.git`、展平仓库或声称可逐字节恢复 LFS 内容。

## 17. 硬件与高风险操作

初始化阶段不会操作硬件。后续普通任务中也必须明确目标和动作：

- 不抢占正在使用的探针、串口或板卡资源。
- 电机、高功率负载首次动作前提示一次风险。
- OTP、eFuse、永久保护/锁定、Option Bytes、Bootloader 区修改和包含重要数据的全片擦除，每次都必须重新确认。

工作区不提供持久化硬件资源锁；多人共享板卡时仍需外部协调。

## 18. 常见停止条件

遇到以下情况，Skill 应停止受影响操作并报告，而不是猜测：

- 路径不存在、不可读、不是本地路径或真实路径不明确。
- Agent 根与用户源存在直接或间接包含。
- 候选目录属于另一个已知活动工作区。
- 源组如何划分或映射不能唯一确定。
- 文件扫描不完整，或源在复制期间发生变化。
- 发现 nested Git、submodule、linked worktree 或 LFS。
- JSON/schema 校验失败。
- 工作区根记录与当前真实根不一致。
- Mutex 超时或共享状态已发生变化。
- 迁移/升级批准摘要已经过期。
- 发布映射陈旧、基线不可达、依赖未固定或用户文件在写入前漂移。
- 自动回滚无法证明安全。

停止不是失败掩盖。回复应列出具体阻断项、已经验证的事实、尚未写入的内容和下一步需要的用户决定。

## 19. 常见问题

### 19.1 为什么不能直接在原工程里建 `.agent` 目录？

当前 Skill 只支持纯净外部工作区。这样可以把用户权威工程、Agent 管理元数据、私有 Git、工作副本和恢复数据分开，降低误提交和误覆盖风险。

### 19.2 为什么初始化后不能打开 workstream 子目录作为 Codex 项目？

子目录不包含完整的本机配置、同步状态和唯一根规则。单独打开会绕过根 `AGENTS.md`，也容易混淆源组私有 Git与 Agent 管理 Git。

### 19.3 用户工程有未提交修改能否初始化？

可以。已保存的 dirty 和必要 untracked 内容可以成为导入基线，但 Skill 不会替用户认领、修复或自动提交这些修改。复杂 Git 拓扑会先暂停并报告。

### 19.4 初始化时构建失败怎么办？

如果工作区布局、映射、Git 和 schema 都有效，构建失败会作为独立事实记录，不必强行修复源码。后续在 workstream 中处理业务问题。

### 19.5 用户拒绝启用用户 Git 会怎样？

工作区仍可正常使用。状态会记录为 `disabled`；未回答则记录为 `deferred`。只有真正向用户工程写入时才需要说明缺少用户 Git 带来的回滚保护差异。

### 19.6 只读检查为什么连日志都不生成？

因为日志、Git 对象、临时计划或刷新后的配置本身也是写入。零写入语义必须完整，才能用于安全审计和预批准阶段。

### 19.7 如何处理迁移前的旧工作区？

旧目录保持原样，只作为按需读取的外部历史参考。不要从旧路径启动日常 Codex，也不要自动扫描、构建、同步或发布。需要修改旧内容时，先复制到当前 workstream 的 reference copy。
