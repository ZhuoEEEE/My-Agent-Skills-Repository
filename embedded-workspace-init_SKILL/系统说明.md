# embedded-workspace-init 系统说明

## 1. 系统职责

`embedded-workspace-init` 是一个仅显式调用的工作区初始化与维护 Skill。

它负责：

- 初始化独立的嵌入式 Agent 工作区。
- 迁移非空或旧 Agent 工作区。
- 刷新已有工作区的源、目标和构建事实。
- 增加或调整源组及其目录映射。
- 管理参考工程的导入、任务副本和正式提升。
- 对工作区规则、结构、policy 和 schema 执行受控升级。
- 部署后续普通 Agent 所需的根规则、配置、指南、工具和 schema。

它不负责日常固件功能开发，也不因初始化而修改用户业务源码、安装工具链或操作硬件。

## 2. 激活规则

该 Skill 的策略为：

```yaml
policy:
  allow_implicit_invocation: false
```

只有用户明确调用 `$embedded-workspace-init` 时才能使用。

不得因为用户提出普通开发、构建、测试或发布请求而自动调用本 Skill。

显式调用也不代表用户授权所有写操作。迁移、策略升级、用户 Git、用户工程发布和参考工程提升仍然受各自的确认边界约束。

## 3. 最高优先级规则

### 3.1 只读模式

用户要求 `read-only`、只读、只检查、不更新状态或语义等价操作时，整个调用零写入。

禁止：

- 创建文件或目录。
- 写临时计划、日志或证据。
- 创建 Git 对象、ref、分支、提交或 worktree。
- 构建或运行生成器。
- 创建备份或恢复快照。
- 更新配置、状态、时间戳或扫描事实。

只读结果只能在回复中返回。

### 3.2 用户权威工程默认只读

用户权威工程只有两类写入入口：

- 已明确授权的 workstream 发布事务。
- 单独授权的用户 Git 操作。

初始化、刷新、迁移、目标发现、构建发现和参考导入不得写用户权威工程。

### 3.3 不猜测安全事实

路径、源分组、映射、Git 拓扑、审批状态或发布方向无法可靠确定时，停止受影响操作并报告。

不得通过放宽验证、手工编辑状态或跳过摘要绑定继续执行。

## 4. Skill 内部资源路由

每次调用先完整读取 `SKILL.md`。

初始化、迁移、刷新或升级请求必须读取：

- `references/lifecycle-and-migration.md`

按当前场景只读取必要的附加 reference：

| 操作场景 | Reference |
| --- | --- |
| 源分组、映射、目标发现、过滤或 Git | `references/sources-targets-and-git.md` |
| Workstream、任务范围、依赖或并发 | `references/workstreams-and-concurrency.md` |
| 导入、发布、冲突、回滚或恢复 | `references/synchronization-and-recovery.md` |
| 构建、生成代码、验证或硬件 | `references/build-and-hardware.md` |
| 参考工程或持久项目知识 | `references/references-and-project-knowledge.md` |
| JSON、状态、schema 或证据 | `references/configuration-schema.md` |
| Skill 自身验收 | `references/acceptance.md` |

不得默认读取全部 references、全部目标、全部 workstream、完整索引、历史事务或所有参考工程正文。

## 5. 启动检查

### 5.1 Skill 根目录

- 从当前 `SKILL.md` 解析 Skill 根目录。
- 使用绝对路径调用 `scripts/` 中的脚本。
- 禁止把 Skill 安装目录本身初始化为 Agent 工作区。

### 5.2 检查范围

只检查用户明确提供的：

- 候选 Agent 工作区。
- 用户权威源。
- 旧 Agent 工作区。
- 已知活动工作区根。
- 参考工程来源。

不得递归扫描整台电脑寻找工程或替代路径。

### 5.3 真实路径

解析所有相关 Windows 本地路径的真实身份，并处理：

- 大小写差异。
- `/` 与 `\` 差异。
- 尾随分隔符。
- 符号链接。
- junction。

拒绝：

- 不存在或不可读的必要路径。
- 网络或 WSL 路径。
- reparse point 身份不明确。
- Agent 根与用户源互相包含。
- 用户源直接作为 integration。
- 候选根位于外层 Codex-managed/permanent worktree。
- 已知的同一用户源多活动工作区。

## 6. 路由选择

使用 `scripts/plan-migration.ps1` 进行只读盘点和路由选择。

在只读请求或安全事实未解决时，它必须是唯一动作。

### 6.1 `new-empty`

目标根为空且路径安全。

在源分组和映射明确后，可使用 `scripts/init-workspace.ps1` 初始化。

### 6.2 `active`

验证现有工作区状态、根身份和版本。

只执行请求范围内的事实刷新。发现布局、policy、固定结构、映射或 schema 变化时，切换到受控升级计划。

### 6.3 `initializing`

只允许：

- 检查。
- 继续同一个已批准初始化。
- 放弃候选。

禁止普通开发、导入和发布。

### 6.4 `nonempty-unmanaged`

只读盘点并要求新的空目标路径。确认前零写入。

### 6.5 `legacy-migration`

生成完整迁移计划和批准摘要。批准后重新盘点，使用 `scripts/apply-migration.ps1` 应用未变化计划。

旧目录始终保持原样。

### 6.6 `policy-upgrade`

展示当前和目标版本、文件操作、Git 影响、快照、验证和回滚计划。批准后使用 `scripts/apply-policy-upgrade.ps1`。

### 6.7 `inside-user-source` 或 `contains-user-source`

不得在候选位置创建任何内容。要求用户选择一个外部空目录。

## 7. 新工作区初始化流程

对允许初始化的空根：

1. 写入前重新解析路径，并确认根仍为空。
2. 创建 `workspace_state: initializing` 的固定骨架。
3. 部署根规则、用户文档、配置、schema、运行指南、工具和模板。
4. 创建 Agent 管理 Git。
5. 为每个确认源组创建 integration 和独立源组私有 Git。
6. 按映射导入已保存、允许纳管且非敏感的文件。
7. 建立可取回的用户同步基线和文件索引。
8. 发现目标和构建候选，不覆盖确认事实。
9. 验证路径、映射、schema、Git 边界和用户源未被写入。
10. 只有全部必要不变量通过后，才原子切换为 `workspace_state: active`。

不得在该流程中初始化用户 Git。

源代码构建失败单独记录，不因业务源码失败而伪造初始化失败或自动修复源码。

## 8. 非空与旧工作区迁移

迁移使用“新路径创建、旧路径保留、验证后激活”的模式。

规划必须包含：

- 旧根和新根的真实路径。
- 源定义和目录映射。
- 旧相对路径到新相对路径的复制分类。
- 排除项、敏感项和未解决项。
- Git 边界。
- 旧规则文件归档。
- 验证方法。
- 失败结果和回滚边界。
- 绑定计划内容的 approval digest。

用户只确认部分内容时，重新生成完整计划，不实施部分迁移。

批准后：

1. 重新读取路径、清单、Git 和源定义。
2. 任一实质变化使批准失效。
3. 提醒用户保存文件并暂停写入旧目录。
4. 在新空根创建 `initializing` 工作区。
5. 只复制已批准映射。
6. 复制期间检测源变化。
7. 归档旧规则，但不把旧规则设为当前指令。
8. 验证成功后激活新根。

失败时旧目录保持不变，新根保持 `initializing`。不得交换、移动、重命名或删除旧目录。

## 9. 源组与映射

### 9.1 Source group

一个源组表示需要共同保持相对拓扑并使用同一私有 Git 的内容集合。

来源类型：

- `user-imported`
- `agent-created`
- `reference-promoted`

`agent-created` 和 `reference-promoted` 默认没有用户 authority mapping，不得虚构用户路径。

### 9.2 Mapping

每个 mapping 包含：

- 稳定 `mapping_id`。
- 本机 `source_path`。
- integration 内的 `integration_subpath`。

可移植身份与拓扑进入 `targets.json`；本机绝对路径只进入被 Git 忽略的 `targets.local.json`。

禁止：

- 绝对 integration path。
- `..` 路径逃逸。
- mappings 的 integration 子路径重叠。
- Agent 根与源路径递归包含。
- 一个受管文件反向映射到多个用户路径。

只有真实拓扑变化才递增 `mapping_revision`。

### 9.3 添加或修改

- 新增 source：`scripts/add-source.ps1`
- 修改 mapping：`scripts/migrate-source-mappings.ps1`

两者都先生成计划和 digest，再使用 `-Apply` 应用未变化的计划。

## 10. 文件导入规则

只枚举用户提供的源路径。

保留：

- 法律和版权文件。
- 启动代码和链接脚本。
- 必需固件 blob 和库。
- 用户已保存并被纳管的 dirty/untracked 内容。

排除或阻止：

- `.git` 元数据。
- IDE 本机 workspace 状态。
- 已确认可重建缓存和输出。
- 私钥、token、凭据和生产签名材料。
- 许可证激活秘密和设备数据转储。

高熵不能单独作为秘密判定。用途不明确的 license 文件进入待确认清单。

导入前后都必须获取文件清单。扫描不完整或源在复制期间变化时，不能建立基线。

不得把过滤、不可读或未扫描项目解释为删除。

## 11. 目标发现

只在已登记 integration 中发现目标，不扫描参考工程正文。

可识别的工程标记包括 Make、CMake、Eclipse、Keil、IAR、MPLAB、ESP-IDF、Zephyr/west、PlatformIO 和 Arduino。

规则：

- 目标使用稳定且可读的 `target_id`。
- 已保存 ID 不因目录名或 IDE 显示名变化而改变。
- 扫描只补充缺失的 detected fact。
- 不覆盖 `provenance: confirmed` 的字段。
- 工具或工程变化把相关事实标为 `stale`，不随意重命名 ID。
- 示例、备份、嵌套入口或冲突事实保留为待确认候选。

使用 `scripts/detect-targets.ps1` 报告或应用发现结果。

## 12. Git 域

### 12.1 Agent 管理 Git

位于工作区根，管理根规则、说明、可移植配置、schema、指南、工具、模板、项目知识、迁移历史、参考包装和 workstream 元数据。

它不管理源码正文、本机配置、动态同步状态、证据正文、恢复数据或构建输出。

每次管理检查点只暂存明确路径。禁止 broad add、commit-all、自动 push 或改写无关历史。

### 12.2 源组私有 Git

每个源组拥有独立且无 push destination 的私有 Git，用于保存 integration、用户同步基线、source checkpoint、workstream branch 和 linked worktree。

### 12.3 用户 Git

用户 Git 可选，并通过 `scripts/set-user-git.ps1` 单独处理。

现有用户 Git 只检查和保护。普通开发和发布不自动 commit 或 push。

为无 Git 用户源启用 Git 前，必须展示 repository root、nested repository 检查、敏感和构建排除项、拟创建的 `.gitignore` 以及 baseline commit 范围。

## 13. Workstream 与并发

每个逻辑任务拥有独立 workstream、分支、linked worktree 和 `workstream.json`。

新任务默认新建。只有用户明确继续某个任务，或 conversation binding 唯一解析时才复用。

Scope 使用 `source_id`、相对路径和 `read|write`。禁止绝对路径、`..`、link escape 和大小写重叠遗漏。

扩大写范围、构建高影响生成区域或发布前，重新检查其他 active/unresolved workstream 的写范围。

每个 source ref 记录：

- `user_baseline_commit`
- `task_base_commit`
- `head_commit`
- `mapping_revision`

依赖必须固定到具体 workstream 和具体提交，拒绝依赖环，不得只记录移动 branch。

相关脚本：

- `scripts/new-workstream.ps1`
- `scripts/update-workstream.ps1`
- `scripts/pin-workstream-dependency.ps1`

## 14. 共享状态互斥

共享配置、mapping、Git ref/worktree、baseline 和 publish/recovery state 只能由受管脚本在工作区 Named Mutex 下修改。

操作顺序：

1. 只读计划。
2. 获取 Mutex。
3. 锁内重读状态和哈希。
4. 确认计划仍有效。
5. 写入并验证。
6. 释放 Mutex。

锁超时报告 `busy`，不得写入共享状态。

Mutex 不能阻止外部编辑器修改用户文件，因此发布和恢复还必须使用逐文件 expected hash。

## 15. 导入与发布

### 15.1 三个方向

- `inspect`：只读比较。
- `import`：用户工程到私有 integration/当前 workstream。
- `publish`：冻结 workstream 到用户工程。

方向不明确时询问一次。明确的 Agent 到用户表达直接进入同一发布流程。

### 15.2 用户导入

使用 `scripts/import-sources.ps1`。

导入前只扫描已登记 mappings。非冲突变化进入源组私有 Git，并创建新的可达用户基线和文件索引。

活动 workstream 先 checkpoint 自身修改，再将任务提交和固定依赖重放到新的用户基线。用户来源内容不得残留在任务发布差异中。

### 15.3 发布规划

使用 `scripts/publish-workstream.ps1` 的规划模式。

发布必须具备：

- 明确 workstream。
- `active` 工作区。
- 当前 mapping revision。
- 完整文件索引。
- 可达 baseline 和依赖提交。
- 范围内修改。
- 冻结且干净的任务内容。
- 无未解决冲突。

发布内容只能来自 `task_base_commit..head_commit` 和固定提交的显式依赖闭包。

逐文件 manifest 记录 source、mapping、相对路径、`add|modify|delete`、baseline/user/Agent/expected hash 以及即时写入前置条件。

完整 dry run 必须在任何用户写入前完成。

### 15.4 发布应用

使用 plan 返回的 manifest digest 再次调用 `scripts/publish-workstream.ps1 -Apply`。

应用顺序：

1. 为全部受影响文件建立恢复快照和 SHA-256 清单。
2. 重新检查所有 manifest precondition。
3. 每个文件写前再次检查 hash。
4. 新增和修改使用同目录临时文件及原子替换。
5. 删除先移入恢复区。
6. 按 frozen manifest 验证结果。
7. 安全可用时执行已登记的用户工程构建。
8. 分别记录文件、构建和副作用状态。

禁止使用目录镜像、隐式删除、时间覆盖、`/MIR` 或 `--delete`。

### 15.5 事务状态

正常状态流：

```text
planned -> backed_up -> applying -> applied -> file_verified -> completed
```

异常或等待状态包括：

- `conflicted`
- `apply_failed`
- `rolled_back`
- `verification_failed`
- `side_effect_review_required`
- `recovery_required`

非终态事务阻止新的 import 和 publish。

### 15.6 失败与恢复

路径、应用或文件验证失败时，只有当前文件仍等于事务预期结果才自动回滚。

无法证明安全或恢复失败时进入 `recovery_required`，不得覆盖现场。

文件正确但用户构建失败时进入 `verification_failed`，等待用户选择保留或回滚。保留只推进用户同步基线，不推进成功构建基线。

## 16. 构建规则

构建配置由稳定 `build_id` 表示，并通过 `scripts/set-build-config.ps1` 登记。

命令必须使用工具 ID、参数数组、相对工作目录和明确执行上下文。

运行使用 `System.Diagnostics.ProcessStartInfo.ArgumentList`。禁止拼接 Shell 命令字符串、`Invoke-Expression`、管道、重定向、`;` 或 `&&` 组合执行。

普通构建只能使用 `agent-copy`。`user-authority` 构建只能由文件已经验证的发布事务调用。

使用 `scripts/invoke-build.ps1` 执行构建并记录证据。

构建成功必须同时满足：

- 命令成功退出。
- 期望 ELF、HEX、BIN 等产物确实生成或更新。
- 没有未分类的工程副作用。

构建变化分类：

- `output_paths`：可重建输出，不进入用户同步基线。
- `generated_write_paths`：已确认生成的工程内容。
- 其他写入：进入 `side_effect_review_required`。

只有真实成功并具有产物证据的构建才能推进成功构建基线。

## 17. IDE、生成代码与硬件

初始化和普通构建使用独立副本，不复用用户工程的旧缓存或 IDE workspace 状态。

默认不重新生成代码。明确要求生成时，先 checkpoint 和 snapshot，只在副本中运行，检查完整差异并保护生成器 user sections。

初始化阶段禁止烧录、擦除、调试或操作板卡。

后续硬件任务必须有明确目标和动作。OTP、eFuse、永久保护、Option Bytes、Bootloader 区和包含重要数据的全片擦除，每次都需要单独确认。

## 18. 参考工程

使用 `scripts/import-reference.ps1` 导入本地目录或固定 Git revision。

Reference wrapper 记录来源、固定版本、获取时间、用途、适用目标、许可证、已知差异以及文件 manifest 和 SHA-256。

参考正文是不可变快照，不参与目标发现、源码 workstream 或用户发布。

需要修改时，使用 `scripts/create-reference-copy.ps1` 创建 workstream 私有副本。

需要成为正式源码时，使用 `scripts/promote-reference.ps1` 创建 `reference-promoted` source。不得自动建立用户 authority mapping。

## 19. JSON、schema 与证据

除 Skill frontmatter 和 `agents/openai.yaml` 外，生成工作区的结构化状态统一使用 UTF-8 JSON 或 JSONL。

JSON 写入必须：

1. 使用显式且足够的序列化深度。
2. 将深度 warning 视为失败。
3. 写入同目录临时文件。
4. 重新解析。
5. 使用 bundled schema 验证。
6. 比较往返后的类型、值、数组长度和对象 key。
7. 验证后原子替换。

任一 JSONL 行无效时，扫描整体不完整，禁止据此推断删除。

证据使用公共信封，原始 stdout、stderr、二进制报告和 vendor log 作为独立 artifact 保存，不把大日志嵌入 JSON。

## 20. 受控升级

任何布局、policy、固定结构、mapping 或 schema 变化都是 managed upgrade。

规划阶段必须展示：

- 当前和目标版本。
- 精确文件操作。
- mapping 和 Git 影响。
- workstream、构建和同步影响。
- checkpoints 和 snapshots。
- 验证和回滚。
- approval digest。

展示计划后停止。确认前不得夹带普通事实刷新。

批准后使用 `scripts/apply-policy-upgrade.ps1`：获取 Mutex、锁内重读、验证计划和 digest、创建检查点及快照、归档旧根规则、应用已定义迁移、验证并记录历史。

未知 policy/schema 版本必须停止。不得推测通用迁移方法。

## 21. 主要脚本

### 生命周期与迁移

- `scripts/plan-migration.ps1`：只读盘点和路由。
- `scripts/init-workspace.ps1`：初始化空工作区。

## 22. 完成条件

初始化或迁移只有在以下事实验证后才可声明完成：

- 工作区真实根正确。
- 状态允许激活。
- 固定骨架完整。
- 只有一个有效根 `AGENTS.md`。
- JSON 和 schema 有效。
- mappings 唯一且可逆。
- Git 域边界正确。
- 用户同步基线可取回。
- 用户权威工程未被初始化流程写入。
- 必要验证完成。
- `workspace_state` 已原子切换为 `active`。

构建失败不应被描述为初始化失败，除非构建是当前操作明确要求的完成条件。

## 23. 最终报告要求

最终回复应说明：

- 选择了哪条路由。
- 创建、迁移或刷新了什么。
- 保留了什么。
- 排除或阻止了什么。
- 当前工作区状态。
- 用户源是否保持未修改。
- 构建是 passed、failed、unavailable 还是 not-run。
- 用户 Git 是 enabled、disabled 还是 deferred。
- 是否存在待确认、冲突或恢复状态。
- 用户后续应从哪个真实根以 `Local` 环境打开 Codex。

文件发布、构建验证和硬件验证必须分别陈述。

没有对应证据时，不得声称初始化、迁移、发布、回滚、构建或硬件验证成功。

## 24. 强制停止条件

以下情况必须停止受影响写入：

- 用户要求只读。
- 路径不可读、非本地或真实身份不明确。
- Agent 根与用户源互相包含。
- 工作区状态不允许该操作。
- 源分组或 mapping 有歧义。
- 源扫描不完整或复制期间变化。
- nested Git、submodule、linked worktree 或 LFS。
- 未知 schema/policy 版本。
- JSON/schema/round-trip 校验失败。
- Mutex 超时。
- approval digest 或 manifest digest 过期。
- baseline 或依赖不可达。
- workstream scope 越界或并发写范围冲突。
- 存在未结束发布事务。
- 用户文件在写入前发生变化。
- 回滚无法证明安全。

停止后不得直接手工修改动态状态继续操作。应报告具体阻断项和下一步所需决定。
