# embedded-workspace-init 系统说明

## 1. 文档定位

本文面向执行、维护或审查 `embedded-workspace-init` Skill 的 Agent 和工程人员，描述当前实际实现的系统边界、决策路由、状态模型、脚本接口、安全不变量、报告要求和验证状态。

权威材料的职责如下：

- `embedded-workspace-init/SPEC.md`：设计、行为范围和验收依据。
- `embedded-workspace-init/OPTIMIZATION_PLAN.md`：轻量化与分层加载的设计背景。
- `built-skills/embedded-workspace-init/SKILL.md`：实际 Skill 的运行入口和最高层指令。
- `built-skills/embedded-workspace-init/references/`：按场景加载的详细运行规则。
- `built-skills/embedded-workspace-init/scripts/`：确定性操作实现。
- `built-skills/embedded-workspace-init/assets/`：初始化到工作区的规则、模板和 schema。

本文用于解释系统，不替代实际 `SKILL.md`，也不应被复制进已初始化工作区作为新的规则文件。运行时以已安装 Skill 内容和目标工作区的受管状态为准。

## 2. 系统角色

系统的职责是创建或维护一个独立的 Windows 嵌入式 Agent 工作区，并使后续普通 Agent 在不依赖日常专用 Skill 的情况下安全完成开发、构建、验证、交接和按需发布。

系统负责：

- 路径和布局安全检查。
- 新工作区初始化。
- 非空/旧工作区迁移规划与应用。
- 用户源分组、可逆映射和过滤导入。
- 目标及构建事实发现。
- Agent 管理 Git 和源组私有 Git 的建立与维护。
- Workstream、范围、依赖和并发元数据。
- 用户工程导入、三方发布、回滚和恢复状态。
- 参考工程包装、任务副本和正式提升。
- 工作区 policy/schema 的受控升级。
- 根规则、用户手册、指南、工具、schema 和固定目录职责的部署。

系统不负责：

- 普通固件功能实现。
- 自行修复业务源码或基线构建错误。
- 自动安装或升级工具链。
- 把工程转换为另一套构建系统。
- 初始化阶段操作硬件。
- 自动创建或提交用户 Git。
- 扫描用户未提供的磁盘范围。
- 提供操作系统级绝对隔离或硬件资源锁。

## 3. 触发策略与授权边界

### 3.1 仅显式调用

`agents/openai.yaml` 设置：

```yaml
policy:
  allow_implicit_invocation: false
```

只有用户明确调用 `$embedded-workspace-init` 时才执行本 Skill。普通固件开发不应自动加载或调用它。

### 3.2 调用不自动扩大授权

显式调用允许系统对用户指定路径进行必要的只读检查，但不自动授权所有写操作：

- 对明确、空的新根执行首次初始化，可在路径和映射无歧义时创建固定骨架。
- 非空/旧工作区迁移必须先给出完整计划并停止，等待明确批准。
- policy、schema、布局、映射或安全规则升级必须先给出完整计划并停止。
- 用户工程发布必须有明确 Agent 到用户工程的发布意图，并绑定具体 workstream 和清单。
- 用户 Git 初始化、提交或推送是独立授权，不得夹带在初始化或发布中。
- 参考工程提升、建立新的用户权威映射和高风险硬件操作均需要独立明确意图。

### 3.3 只读覆盖一切写入

用户说“只读”“只检查”“不更新状态”或语义等价表达时，整个操作必须零写入：

- 不创建目录或文件。
- 不生成临时计划文件、日志、证据或恢复快照。
- 不创建 Git 对象、ref、分支、worktree 或提交。
- 不执行构建、生成器或任何会产生输出的命令。
- 不更新目标、时间戳、事实、配置或扫描缓存。

只读规划结果只能在回复中返回。

## 4. 指令加载策略

每次调用先完整读取实际 Skill 的 `SKILL.md`。初始化、迁移、刷新或策略升级必须读取：

- `references/lifecycle-and-migration.md`

然后只读取当前操作需要的附加指南：

| 场景 | 必读 reference |
| --- | --- |
| 源分组、目录映射、目标发现、导入过滤或 Git | `sources-targets-and-git.md` |
| Workstream、任务范围、依赖或并发 | `workstreams-and-concurrency.md` |
| 导入、发布、冲突、回滚或恢复 | `synchronization-and-recovery.md` |
| 构建发现、执行、生成代码或硬件验证 | `build-and-hardware.md` |
| 参考工程或持久项目知识 | `references-and-project-knowledge.md` |
| JSON 字段、状态、schema 或证据 | `configuration-schema.md` |
| Skill 实现验收或发布 | `acceptance.md` |

不得因为 reference 文件存在而一次读取全部内容。普通操作也不得默认加载全部目标、workstream、索引、历史事务、旧工作区或参考工程正文。

## 5. 初始检查顺序

### 5.1 解析 Skill 与候选路径

1. 从当前 `SKILL.md` 解析已安装 Skill 根目录。
2. 初始化前脚本使用该 Skill 根下的绝对路径。
3. 禁止把已安装 Skill 自身目录作为待初始化工作区。
4. 只解析用户提供的候选 Agent 根、用户源、旧工作区和已知活动根。
5. 不扫描整台机器寻找替代路径。

### 5.2 真实路径和包含关系

对每个路径执行本地真实路径解析，规范化大小写、目录分隔符、尾随分隔符、symlink 和 junction。拒绝：

- 不存在或不可读路径。
- 网络/WSL 路径。
- reparse point 无法确定的路径。
- Agent 根与任何用户源互相包含。
- 用户源直接作为 integration 副本。
- 同一用户源已知属于另一个活动工作区。
- Agent 根位于外层 Codex-managed/permanent worktree。

无法证明路径安全时，只报告解析事实并停止受影响操作。

### 5.3 候选根分类

使用 `scripts/plan-migration.ps1` 进行只读盘点和路由。候选结果应归入：

- `new-empty`
- `active`
- `initializing`
- `nonempty-unmanaged`
- `legacy-migration`
- `policy-upgrade`
- `inside-user-source`
- `contains-user-source`

`plan-migration.ps1` 在只读模式或安全事实未解决时必须是唯一动作。

## 6. 路由状态机

### 6.1 `new-empty`

前提：目标根为空、路径安全、源分组与映射无歧义。

行为：

1. 写入前重新解析并确认目录仍为空。
2. 使用 `init-workspace.ps1` 创建 `initializing` 工作区。
3. 部署根文档、固定骨架、指南、工具、schema 和模板。
4. 创建 Agent 管理 Git。
5. 对确认的源组创建 integration 和独立源组私有 Git。
6. 过滤导入已保存内容，创建用户同步基线和索引。
7. 检测目标候选，不覆盖确认事实。
8. 验证安全不变量。
9. 仅在验证通过后切换为 `active`。

不得在初始化流程中创建用户 Git。

### 6.2 `active`

先验证：

- `workspace.json` schema。
- `workspace_state: active`。
- `layout_mode: pure`。
- `managed_root: .`。
- `targets.local.json` 中登记的真实根与当前根一致。
- policy/schema 版本已知。

只执行用户请求范围内的事实刷新。若检测到布局、policy、固定结构、映射或 schema 变化，整个操作切换为受控升级规划，不能顺带写入普通事实。

### 6.3 `initializing`

只允许：

- 检查当前状态。
- 继续同一个已批准初始化。
- 放弃候选工作区。

禁止普通开发、用户源导入和发布。

### 6.4 `nonempty-unmanaged` 或 `legacy-migration`

第一次调用只输出完整迁移计划和批准摘要，不做任何写入。计划至少包含：

- 旧、新真实路径。
- 源定义和可逆复制映射。
- 排除项、未解决项和敏感项。
- Git 边界。
- 旧规则归档。
- 对工作区、构建、同步和历史的影响。
- 验证、失败处理和回滚。

用户批准后重新盘点。路径、文件哈希、Git 状态、源定义或摘要变化会使批准失效。应用时旧目录保持原样，新目录失败则保持 `initializing`。

### 6.5 路径位于用户源内部或包含用户源

不得创建任何内容。仅报告冲突，要求用户选择一个外部空目录并重新生成完整计划。

### 6.6 Reference import

读取 reference 指南，使用 `import-reference.ps1`。参考正文不得进入源/目标发现或发布。

## 7. 源组与映射模型

### 7.1 源组

一个 source group 表示需要共同保留相对拓扑并共享一个私有 Git 的内容集合。使用稳定 `source_id`。

分组原则：

- 合理共同产品根且不包含大量无关树时，可作为一个源组。
- 完全独立的分散工程使用不同源组。
- 分散目录共享相对依赖或生成配置时，使用同一源组的多个 mapping。
- 不为方便而复制一个庞大的无关共同父目录。

### 7.2 Mapping

每个 mapping 具有稳定 `mapping_id`、非重叠的 `integration_subpath` 和本机 `source_path`。

- 可移植身份和拓扑写入 `targets.json`。
- 绝对路径只写入被 Git 忽略的 `targets.local.json`。
- 禁止绝对 integration 子路径、`..`、重叠子路径和递归包含。
- 每个参与同步的 integration 文件必须唯一反向映射到一个权威路径。
- 只有真实拓扑变化才递增 `mapping_revision`。

### 7.3 来源类型

- `user-imported`：有外部 authority mapping，显式发布，支持三方同步。
- `agent-created`：`user_source: none`、`sync_strategy: none`、空 mappings，不提示用户 Git。
- `reference-promoted`：由参考工程明确提升，默认仍无用户源和发布映射。

不得为后两类来源虚构用户路径。之后建立外部 authority mapping 必须使用单独的 digest-bound 映射迁移计划。

## 8. 导入过滤规则

只枚举用户提供的根。导入前后都生成文件清单；快照变化或不完整时不能成为基线。

保留：

- `LICENSE`、`NOTICE`、`COPYING` 和版权清单。
- 启动文件、链接脚本、必要固件 blob 和依赖库。
- 用户已保存且被纳管的 dirty/untracked 内容。

排除或阻止：

- `.git` 元数据。
- Eclipse `.metadata` 等本机 IDE workspace 状态。
- 已知可重建缓存和输出。
- 私钥、token、凭据、生产签名材料、许可证激活秘密和设备转储。

高熵只是警告，不能单独作为排除依据。`license` 既可能是法律文件也可能是秘密，语义不清时列为 unresolved。外部 symlink/junction 扩展暂停处理；不得静默复制 SDK 或无关目录。

## 9. 目标与构建事实

仅在已登记 integration 中发现目标，不扫描 `reference-projects/`。识别标记包括 Make、CMake、Eclipse、Keil、IAR、MPLAB、ESP-IDF、Zephyr/west、PlatformIO 和 Arduino 等工程元数据。

- `target_id` 稳定且可读，碰撞时加最小必要后缀。
- 已保存 ID 不因目录或 IDE 显示名变化而重命名。
- 新扫描只补充缺失 detected fact，不覆盖 `provenance: confirmed`。
- 备份/示例、嵌套入口、移动/拆分工程和冲突事实保持 candidate，等待确认。
- `build_id` 表示稳定构建配置，例如 `debug`、`release`。
- 工具、工程或依赖变化时，保留原值并将相关事实标为 `stale`。

构建命令必须存储为工具 ID、参数数组和相对 `cwd`。运行使用 `ProcessStartInfo.ArgumentList`，禁止拼接 Shell 字符串、`Invoke-Expression`、管道、重定向、`;` 或 `&&`。

## 10. 三个 Git 域

### 10.1 Agent 管理 Git

位于工作区根，只跟踪管理元数据、规则、可移植配置、schema、指南、模板、项目知识、迁移历史、参考包装和 workstream 元数据。

必须忽略：

- integration 和私有 worktree 正文。
- reference body。
- `targets.local.json` 等本机配置。
- 动态同步状态、索引、事务、证据正文、恢复数据、IDE 状态和输出。

每次检查点只暂存明确操作路径，禁止 broad add、commit-all、自动 push 或改写无关历史。

### 10.2 源组私有 Git

每个受支持源组必须独立，无 push destination。它保存：

- integration 内容。
- 不可变且可达的用户同步基线 ref。
- source checkpoints。
- workstream branches。
- `work/<id>/sources/<source-id>/` linked worktrees。

用户 Git 的提交不得出现在私有仓库，私有提交也不得写回用户 Git。

### 10.3 用户 Git

用户 Git 是可选且单独授权的。现有 Git 只检查和保护；普通开发与发布都不自动 commit 或 push。

无 Git 时，启用计划必须显示：

- 精确 repository root。
- nested repository 检查结果。
- 敏感文件和构建产物排除。
- 拟创建的 `.gitignore`。
- 首次 baseline commit 内容。

用户拒绝记录为 `disabled`，未回应记录为 `deferred`，都不阻止 Agent 工作区初始化。

## 11. Workstream 与并发

每个逻辑任务拥有：

- `work/<workstream-id>/`。
- 每个涉及源组的独立 branch 和 linked worktree。
- 一个 schema-valid `workstream.json`。
- 一个简洁的人类交接 README。

新任务默认新建。仅用户明确继续某个任务，或 conversation binding 唯一解析时复用。conversation host/thread ID 是提示，不是主身份。

Scope 使用 `source_id + normalized relative path + read|write`。禁止绝对路径、`..`、link escape 和大小写重叠遗漏。扩大写范围、构建高影响生成器区域或发布前必须重新检查其他 active/unresolved workstream。

每个源 ref 记录：

- `user_baseline_commit`
- `task_base_commit`
- `head_commit`
- `mapping_revision`

依赖必须固定到具体 workstream、每个源的具体提交和映射版本；禁止只依赖移动 branch，并拒绝依赖环。

### 11.1 工作区 Mutex

所有共享配置、mapping、Git ref/worktree、baseline、publish/recovery state 变更通过一个 Windows Named Mutex 串行化：

```text
Local\embedded-workspace-init-<normalized-real-root-sha256-prefix>
```

正确顺序：

1. 只读计划。
2. 获取 Mutex。
3. 在锁内重新读取所有相关状态和哈希。
4. 验证计划仍有效。
5. 写入并验证。
6. 释放 Mutex。

超时返回 `busy` 且不写共享状态。Mutex 不能防止外部编辑器改文件，因此发布和恢复还必须使用逐文件 expected hash。

## 12. 同步与发布事务

### 12.1 状态来源

- 每源同步状态：`workspace-management/sync-state/sources/<source-id>.json`
- 文件索引：`workspace-management/indexes/<source-id>.jsonl`
- 发布事务：`workspace-management/transactions/<publish-id>.json`
- 任务状态：`work/<workstream-id>/workstream.json`

不得创建 `sync-state/workstreams/` 缓存。逐源比较从上述权威状态按需计算。

### 12.2 Import

导入前只扫描已登记 mappings。无 Git 时先比较类型、大小和 mtime，再对候选变化计算哈希。不完整扫描不能推断删除。

非冲突的用户变化进入 integration/private Git，并产生新的可达 user baseline 和文件索引。活动 workstream 需要先 checkpoint 自己的修改，再把任务和固定依赖重放到新的用户基线上。用户来源内容不能残留在 `task_base_commit..head_commit`。

### 12.3 Publish 规划

发布必须有明确方向和当前 workstream。锁内拒绝：

- 非 active 或 recovery-blocked 工作区。
- stale mapping。
- 不完整索引。
- 不可达 baseline/dependency。
- 超出 scope 的修改。
- 未冻结 dirty task content。
- 三方冲突或用户文件漂移。

冻结 `head_commit` 后，只从 `task_base_commit..head_commit` 和 pinned dependency closure 计算内容。事务清单逐文件记录 mapping、relative path、`add|modify|delete`、baseline/user/Agent/expected hashes 和即时写入前置条件。

### 12.4 Apply

任何用户写入前必须完成全部源的 dry run 和恢复快照。然后：

1. 再次检查所有清单前置条件。
2. 每个文件写前再次检查 hash。
3. 修改/新增使用同目录临时文件和原子替换。
4. 删除先移入恢复区。
5. 所有结果按 frozen manifest 校验。
6. 可安全执行时运行已登记的 user-authority build。
7. 分别记录 file、build、side-effect 状态。

典型状态：

```text
planned -> backed_up -> applying -> applied -> file_verified -> completed
```

其他终态或阻断态包括：

- `conflicted`
- `apply_failed`
- `rolled_back`
- `verification_failed`
- `side_effect_review_required`
- `recovery_required`

非终态事务阻止新的 import/publish。

### 12.5 Failure

路径、应用或文件验证失败时，只有当前文件仍等于事务 expected result 才自动回滚。恢复后逐文件验证，baseline 不变。

外部写入导致无法证明安全，或恢复失败时，进入 `recovery_required`，不覆盖当前现场。文件正确但 user build 失败时进入 `verification_failed`，等待用户选择保留或回滚。保留只推进用户同步基线，不推进成功构建基线。

## 13. 构建与副作用

正常构建仅允许 `execution_context: agent-copy`。`user-authority` 只允许由已冻结发布事务在文件验证后调用。

构建证据至少记录：

- executable 和版本。
- 实际 PowerShell executable 和版本。
- target/build IDs。
- commit 和 execution context。
- `cwd` 与参数数组。
- exit code。
- stdout/stderr artifact references。
- 构建前后文件变化。
- 期望产物 hash。

退出码为零但未生成或更新期望 ELF/HEX/BIN 不能算通过。

构建变化分类：

- `output_paths`：可丢弃输出，不进入用户同步基线。
- `generated_write_paths`：已确认生成的工程内容；成功时可进入新的用户基线，但不进入任务发布差异。
- 其他项目/配置/IDE 写入：进入 `side_effect_review_required`，阻止 baseline 推进和新同步，等待分类或恢复。

失败构建修改 generated path 时保持 `verification_failed`。只有实际成功并有期望产物证据的构建才能推进 `last_successful_build_commit`。

## 14. JSON、schema 与证据

除 Skill frontmatter 和 `agents/openai.yaml` 外，工作区结构化状态统一为 UTF-8 JSON/JSONL，不增加 YAML 运行依赖。

所有 JSON 写入必须：

1. 使用显式、足够的 serialization depth。
2. 将深度 warning 视为失败。
3. 写入同目录临时文件。
4. 重新解析。
5. 使用 bundled schema 验证。
6. 深度比较类型、值、数组长度和对象 key。
7. 验证通过后原子替换。

任一 JSONL 行无法解析时，扫描整体不完整，禁止由此推断删除。

Evidence 公共信封包括：

- `schema`
- `evidence_id`
- `kind`
- `captured_at`
- `subject`
- `result`
- `artifacts`

原始 stdout、stderr、二进制报告和 vendor log 作为独立 artifact 保存，用相对路径、media type、size 和可用 SHA-256 引用；不把大日志嵌进 JSON。

## 15. 参考工程与项目知识

### 15.1 Reference snapshot

结构为：

```text
reference-projects/<reference-id>/
|-- README.md
|-- manifest.json
`-- project/
```

Wrapper 和 manifest 由 Agent 管理 Git 跟踪，body 被忽略。Body 是过滤后的不可变快照，不参与目标发现、workstream source branch 或发布。

可修改副本位于 `work/<workstream-id>/reference-copies/<reference-id>/project/`，具有独立 no-push private Git、来源和清理条件。

Promotion 需要明确意图，生成 `reference-promoted` 源组。默认保持 `user_source: none`、空 mappings 和不可发布状态。

### 15.2 Durable knowledge

- `PRODUCT.md`：长期产品目标和能力边界。
- `SOLUTION.md`：当前有效系统方案。
- `ROADMAP.md`：阶段、依赖、退出条件和下一步。
- `decisions/`：跨任务选择、权衡、证据和替代关系。
- `versions/`：版本目标、包含/排除范围和验证标准。

Workstream 结论在用户确认前不是项目事实。初始化只创建目录职责和模板，不创建空正文实例。

## 16. 策略与 schema 升级

任何 layout、policy、fixed structure、mapping 或 schema 变化都是 managed upgrade。

规划阶段必须展示：

- 当前与目标 `workspace_schema`、`policy_version`。
- 精确文件/目录操作。
- mapping 和 Git 影响。
- workstream、build、sync 影响。
- snapshots、验证和 rollback。
- 绑定完整计划的 digest。

展示后停止等待批准。确认前不得混入事实刷新。批准后 `apply-policy-upgrade.ps1` 获取 Mutex、锁内重读、验证 digest、为明确受影响路径创建 checkpoints/snapshots、归档被替换的根规则、应用已定义的版本迁移、验证并记录历史。

当前版本不提供任意未来 schema 的通用转换器。未知版本必须停止。

## 17. 脚本接口

以下为 `built-skills/embedded-workspace-init/scripts/` 当前实现。初始化完成后，对应运行工具部署到目标工作区的 `workspace-management/tools/`。Agent 应使用绝对路径调用，并始终明确 `-WorkspaceRoot` 或脚本要求的计划载荷。

### 17.1 生命周期

| 脚本 | 作用 | 写入语义 |
| --- | --- | --- |
| `plan-migration.ps1` | 盘点候选根、生成迁移或 policy upgrade 计划 | 始终只读 |
| `init-workspace.ps1` | 初始化空根；可继续 `initializing` 状态 | 直接写入；仅用于已授权初始化 |
| `apply-migration.ps1` | 应用 Base64 计划载荷 | 必须提供匹配的 `ApprovalDigest` |
| `refresh-workspace.ps1` | 计划或执行事实刷新，可指定导入源 | 无 `-Apply` 只规划；`-Apply` 写入 |
| `apply-policy-upgrade.ps1` | 应用已批准 policy upgrade | 必须提供匹配的 `ApprovalDigest` |

重要参数：

```powershell
plan-migration.ps1 -WorkspaceRoot <path> [-UserSourcePath <paths>] [-LegacyWorkspaceRoot <path>] [-SourceDefinitionsJson <json>] [-CopyMappingsJson <json>] [-KnownActiveWorkspaceRoot <paths>] [-LegacyRuleFile <paths>] [-PolicyUpgrade]

init-workspace.ps1 -WorkspaceRoot <path> [-UserSourcePath <paths>] [-SourceDefinitionsJson <json>] [-KnownActiveWorkspaceRoot <paths>] [-ResumeInitializing] [-LeaveInitializing]

apply-migration.ps1 -PlanBase64 <payload> -ApprovalDigest <sha256>
```

### 17.2 源、映射与目标

| 脚本 | 作用 | 写入语义 |
| --- | --- | --- |
| `add-source.ps1` | 添加 user-imported 或 agent-created source | 无 `-Apply` 规划；`-Apply` 且 digest 匹配后写入 |
| `migrate-source-mappings.ps1` | 增加 authority mapping 或改变 topology | 无 `-Apply` 规划；`-Apply` 且 digest 匹配后写入 |
| `import-sources.ps1` | 扫描并导入某 source 的已保存变化 | 无 `-Apply` 规划；`-Apply` 写入 |
| `detect-targets.ps1` | 发现目标候选 | 默认报告；`-Apply` 更新事实 |
| `set-build-config.ps1` | 登记/更新 target 的 build configuration | 无 `-Apply` 规划；`-Apply` 且 digest 匹配后写入 |
| `set-user-git.ps1` | 单独启用或禁用用户 Git | 无 `-Apply` 规划；`-Apply` 写入 |

重要参数：

```powershell
add-source.ps1 -WorkspaceRoot <path> -SourceDefinitionJson <json> [-ExpectedPlanDigest <sha256>] [-Apply]

migrate-source-mappings.ps1 -WorkspaceRoot <path> -SourceId <id> -MappingsJson <json> [-ExpectedPlanDigest <sha256>] [-Apply]

import-sources.ps1 -WorkspaceRoot <path> -SourceId <id> [-Apply]

set-build-config.ps1 -WorkspaceRoot <path> -TargetId <id> -ConfigurationJson <json> [-Provenance detected|confirmed|imported] [-ExpectedPlanDigest <sha256>] [-Apply]

set-user-git.ps1 -WorkspaceRoot <path> -SourceId <id> -Decision Enable|Disable [-MappingId <id>] [-Apply]
```

`SourceDefinitionsJson` 使用对象或对象数组。一个用户导入源和一个 Agent 自建源的形状如下；实际调用时 `source_path` 必须替换为已解析的本地路径：

```json
[
  {
    "id": "motor-firmware",
    "origin": "user-imported",
    "user_source": "configured",
    "mappings": [
      {
        "id": "motor-root",
        "source_path": "D:/Firmware/Motor",
        "integration_subpath": "."
      }
    ]
  },
  {
    "id": "agent-tools",
    "origin": "agent-created",
    "user_source": "none",
    "mappings": []
  }
]
```

`id` 和 mapping `id` 必须全局有效且不重复。`user_source: configured` 至少需要一个 mapping；`user_source: none` 必须使用空 mappings。`integration_subpath` 是 integration 内的相对路径，多个 mapping 之间不能重叠。

`ConfigurationJson` 至少表达稳定 build ID、显示名、相对工作目录、结构化命令和状态。例如：

```json
{
  "build_id": "debug",
  "configuration": "Debug",
  "cwd": ".",
  "command": {
    "tool": "cmake",
    "args": ["--build", "build", "--config", "Debug"]
  },
  "command_state": "candidate",
  "tool_executable": "C:/Program Files/CMake/bin/cmake.exe",
  "tool_version": "4.1.1",
  "output_paths": [],
  "generated_write_paths": [],
  "outputs": ["build/motor.elf"]
}
```

注册时不能直接声称 `command_state: verified`；只有实际成功的 evidence run 才能提升。可运行的 `candidate|unconfirmed|stale` 工具必须已在本机配置中登记，或在 JSON 中提供 `tool_executable`。非空 `output_paths` 和 `generated_write_paths` 只能以 `-Provenance confirmed` 保存，且两类路径不能重叠。

### 17.3 Workstream 与构建

| 脚本 | 作用 | 写入语义 |
| --- | --- | --- |
| `new-workstream.ps1` | 新建或明确复用 workstream | 直接写入共享状态和 worktree |
| `update-workstream.ps1` | 更新 scope、status 或 unresolved state | 直接写入 |
| `pin-workstream-dependency.ps1` | 规划/固定具体依赖提交 | 无 `-Apply` 规划；`-Apply` 写入 |
| `invoke-build.ps1` | 执行已登记构建并记录证据 | 会运行构建；不是只读命令 |

重要参数：

```powershell
new-workstream.ps1 -WorkspaceRoot <path> -Title <title> -ScopeJson <json>
new-workstream.ps1 -WorkspaceRoot <path> -ReuseWorkstreamId <id>

update-workstream.ps1 -WorkspaceRoot <path> -WorkstreamId <id> [-ScopeJson <json>] [-Status active|paused|blocked|completed|abandoned] [-HasUnresolvedChanges <bool>]

pin-workstream-dependency.ps1 -WorkspaceRoot <path> -WorkstreamId <id> -DependencyWorkstreamId <id> [-Apply]

invoke-build.ps1 -WorkspaceRoot <path> -TargetId <id> -BuildId <id> [-BuildContext agent-copy|user-authority] [-WorkstreamId <id>] [-PublishId <id>] [-AllowCandidate]
```

`ScopeJson` 是数组，每个 source 在一个 workstream 中只能出现一次。每项必须给出 target 列表和至少一个显式相对路径：

```json
[
  {
    "source_id": "motor-firmware",
    "targets": ["motor-controller"],
    "paths": [
      { "path": "src", "access": "write" },
      { "path": "config", "access": "read" }
    ]
  }
]
```

目标必须属于同一 `source_id`；路径可以使用 `.` 表示整个 source，但不得使用绝对路径或 `..`。两个 active/unresolved workstream 的 write path 重叠时，脚本会报告冲突。

`-AllowCandidate` 只允许执行尚未验证的候选命令；一次真实成功且存在期望产物证据后，才能把同一稳定 build ID 提升为 verified。

### 17.4 Publish 与恢复

`publish-workstream.ps1` 具有四种模式：

```powershell
# 只读规划并输出 frozen manifest digest
publish-workstream.ps1 -WorkspaceRoot <path> -WorkstreamId <id>

# 应用未变化的计划
publish-workstream.ps1 -WorkspaceRoot <path> -WorkstreamId <id> -ExpectedManifestDigest <sha256> -Apply [-RequireUserBuild]

# 回滚某事务
publish-workstream.ps1 -WorkspaceRoot <path> -PublishId <id> -Rollback

# 接受已验证文件但构建未通过/不可用的结果
publish-workstream.ps1 -WorkspaceRoot <path> -PublishId <id> -Finalize [-AcceptUnverifiedBuild]
```

不得跳过 plan/digest 直接应用。Rollback 和 Finalize 都必须重新获取 Mutex 并核对现场哈希。

### 17.5 Reference

| 脚本 | 作用 | 写入语义 |
| --- | --- | --- |
| `import-reference.ps1` | 从本地路径或固定 Git revision 导入 reference | 无 `-Apply` 规划；`-Apply` 写入 |
| `create-reference-copy.ps1` | 在 workstream 中创建可修改副本和私有 Git | 直接写入 |
| `promote-reference.ps1` | 将 reference 提升为正式 source | 无 `-Apply` 规划；`-Apply` 写入 |

重要参数：

```powershell
import-reference.ps1 -WorkspaceRoot <path> -ReferenceId <id> -SourcePath <path> -Purpose <text> [-ApplicableTarget <ids>] [-License <text>] [-KnownDifferences <text>] [-Apply]

import-reference.ps1 -WorkspaceRoot <path> -ReferenceId <id> -SourceUrl <url> -Revision <commit-or-tag> -Purpose <text> [-Apply]

create-reference-copy.ps1 -WorkspaceRoot <path> -WorkstreamId <id> -ReferenceId <id> -Purpose <text> [-CleanupCondition <text>]

promote-reference.ps1 -WorkspaceRoot <path> -ReferenceId <id> -SourceId <id> [-Apply]
```

### 17.6 通用参数

多数写共享状态的脚本支持：

```powershell
-MutexTimeoutSeconds 30
```

超时表示 `busy`，不得绕过 Mutex 手工修改 JSON、Git refs 或事务状态。

## 18. 根工作区运行规则

初始化生成的根 `AGENTS.md` 是唯一有效的工作区级规则。不得创建根 `AGENTS.override.md`，也不得向 integration 或 linked worktree 额外生成 Agent 规则。

普通任务开始时必须：

1. 读取 `workspace.json`，要求 `active/pure/.`。
2. 读取 `targets.local.json`，确认真实根一致。
3. 如果只读，立即切换零写入。
4. 只加载当前 source/target/build/workstream 和一份必要指南。
5. 以报告模式做轻量源/目标变化检测。
6. 非只读时，仅通过受管脚本导入已保存用户变化。
7. 新建或明确复用 workstream，并检查范围冲突。

用户工程自带的 `AGENTS.md` 等文件是受保护工程内容，不是当前工作区 policy。迁移归档的旧规则也只是审计材料，除非用户明确要求，否则不加载为指令。

## 19. 完成条件与报告格式

初始化或迁移只有在以下事实验证后才可声明完成：

- 工作区真实根正确。
- JSON/JSONL 通过 schema 和 round-trip 校验。
- 固定骨架和职责 README 完整。
- 根只有一个有效 `AGENTS.md`。
- 指南/模板 hash 与部署内容一致。
- 三个 Git 域边界正确。
- 每个用户源有可达 baseline ref。
- mappings 可逆且唯一。
- 用户权威工程在布局初始化中未被写入。
- 必要状态已原子切换为 `active`。

最终回复至少区分：

- 创建或刷新了什么。
- 明确保留了什么。
- 因过滤或风险排除了什么。
- 当前 workspace state。
- build evidence 是 passed、failed、unavailable 还是 not-run。
- 用户 Git 是 enabled、disabled 还是 deferred。
- 哪些能力因真实环境、复杂拓扑或未通过专项验证而阻断。
- 用户下一次应从哪个真实根以 `Local` 打开 Codex。

不得在没有证据时声称构建、硬件测试、迁移、回滚或发布成功。文件发布、构建验证和硬件验证必须分别陈述。

## 20. 停止条件

出现以下任一情况时，停止相关写入并报告：

- 只读请求。
- 路径不可读、非本地、real path 不确定或递归包含。
- 根路径与登记值不一致。
- `workspace_state` 不允许该操作。
- 源分组或 mapping 有歧义。
- 源快照不完整或复制过程中变化。
- nested Git、submodule、linked worktree 或 LFS。
- 未知 schema/policy version。
- schema 或 JSON round-trip 失败。
- Mutex 超时。
- 审批 digest、manifest digest 或文件 hash 过期。
- baseline/dependency 不可达。
- scope 越界或并发写范围冲突。
- 非终态发布事务。
- rollback 无法证明安全。
- 用户工程或旧工作区路径当前不可读。

不要通过手工编辑动态状态、放宽路径校验、忽略 hash 或删除安全机制继续推进。

## 22. 维护原则

- `SKILL.md` 保持为短路由入口，条件细节留在对应 reference。
- 根 `AGENTS.md` 只保存长期不变量和运行指南路由。
- 每条机器事实只保留一个权威来源，不在 Markdown 重复动态状态。
- 确定性、重复性和安全关键操作放在脚本中。
- 新增脚本参数、状态、schema 或用户流程时，同步更新对应 reference、asset、测试和本文档。
- 不因追求文件数、行数或 token 预算删除路径隔离、基线、Mutex、hash、snapshot、atomic replace、rollback 或敏感内容过滤。
- 只为真实出现的版本变化实现确定性迁移，不预先增加通用未来迁移框架。
