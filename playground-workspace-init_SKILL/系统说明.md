# playground-workspace-init 系统说明

## 系统目标

`playground-workspace-init` 是一个仅显式调用的 Codex Skill，用于建立和维护短生命周期、多主题工作区的目录规范。系统将“确定性的文件系统操作”和“需要理解语义的内容决策”分离：Python 脚本负责创建、替换已识别托管区块、话题目录分配和索引刷新；模型负责判断工作区归属、合并无标记文档以及处理实质冲突。

设计规范位于本目录的 `SPEC.md`，实际 Skill 位于 `../built-skills/playground-workspace-init/`。

## 设计原则

系统实现围绕以下原则展开：

1. **显式启用**：Skill 不参与普通请求的隐式路由，只有用户明确选择或提及时才执行工作区初始化和升级。
2. **不接管既有内容**：名称相似、路径相邻或日期格式匹配都不足以证明文件归属。
3. **确定性操作脚本化**：模板读取、区块替换、目录竞争、索引生成和原子写入由脚本完成。
4. **语义决策由模型完成**：无标记文档合并、规则冲突、对话归属和目录重命名需要理解上下文，不能交给字符串匹配。
5. **托管范围最小化**：升级只替换带明确标记的区块，不整份重写用户文档。
6. **重复执行幂等**：相同输入状态下再次初始化不会产生重复规则、目录或索引项。
7. **失败前预检**：初始化先检查所有受管目标；如果存在无标记文件，整轮不写入，避免部分更新。
8. **保持可恢复性**：受管文档使用原子写入，新话题创建失败时撤回本轮创建的 README 和空目录。

## 系统边界

该 Skill 管理的是工作区约定，不是具体话题任务的执行器。它负责：

- 建立或升级根规则、工作区说明和固定管理目录；
- 为新对话分配唯一的话题目录；
- 维护受管话题索引；
- 提供后续对话所需的长期规则和话题上下文模板。

它不负责：

- 决定具体任务使用何种语言、框架或项目结构；
- 自动重构、归档或迁移已有项目；
- 建立或管理 Git 历史；
- 自动删除话题目录；
- 推断相似目录的所有权；
- 替代用户对高影响文件操作的明确授权。

## 调用与生效链路

系统分为两个时间阶段：

```text
用户显式调用 Skill
        |
        v
模型读取 SKILL.md 并执行初始化/升级
        |
        v
脚本写入目标根 AGENTS.md 和 README
        |
        v
后续对话自动读取根 AGENTS.md
        |
        v
新话题创建、续接复用、文件归位和完成检查持续生效
```

Skill 本身只在显式调用时运行，但它写入的根 `AGENTS.md` 是后续行为的长期载体。因此，关闭隐式调用并不意味着初始化后的规则失效；后续对话遵守的是目标工作区内的规则文件。

## 模板内容职责

### 根 AGENTS 模板

`assets/AGENTS.md` 定义四组持久规则：

- 对话归属：区分管理对话、新对话和续接对话；
- 话题命名与文档：约束显式重命名、README 字段和更新时机；
- 文件放置：约束一次性脚本、多文件工具、外部资料和既有项目文件；
- 安全与完成检查：约束删除、跨话题移动、Git 历史和索引同步。

### 根 README 模板

`assets/workspace-README.md` 包含两个独立托管区块：

- `overview`：稳定的工作区用途与目录约定；
- `topic-index`：每次扫描生成的动态话题链接列表。

把二者拆分为独立区块，可以在刷新索引时保持区块外用户说明不变，同时允许规范升级更新概述。

### 工作区管理模板

`assets/workspace-management-README.md` 标识该目录是唯一不带日期前缀的固定管理目录，并记录规范版本、当前状态和待办。初始化、升级和纯维护不创建日期话题目录。

### 话题模板

`assets/topic-README.md` 使用单行版本标记，而不是成对托管区块。创建时替换四个占位符：

| 占位符 | 数据来源 |
| --- | --- |
| `{{CREATED_DATE}}` | `--date` 参数，未提供时取本地当前日期。 |
| `{{CREATED_TIME}}` | 本地当前时间，精确到秒并包含时区偏移。 |
| `{{CONVERSATION_ID}}` | `--conversation-id` 参数，未提供时写 `Unavailable`。 |
| `{{INITIAL_DIRECTORY}}` | 原子创建成功后的目录名。 |

话题 README 后续由模型按实际进展维护，脚本不自动重写其中的状态、目标或产物。

## 运行要求

- Python 3.10 或更高版本。
- 对目标工作区具有所需的读取和写入权限。
- 目标工作区必须已经存在且为目录。
- 脚本必须从实际 Skill 目录调用；它会拒绝把 Skill 自身安装目录当作目标工作区。

脚本不依赖第三方 Python 包。

所有受管文本按 UTF-8 读取和写入。写入时统一使用 LF 换行；已有文件在合并前会将 CRLF 和 CR 归一化为 LF。因此，更新含托管区块的文件时，即使语义内容相同，原文件的换行形式也可能被规范化。

## 脚本常量与匹配规则

`init_workspace.py` 的关键常量如下：

| 常量 | 当前值 | 作用 |
| --- | --- | --- |
| `VERSION` | `"1"` | 输出当前规范版本，并用于模板版本管理。 |
| `MARKER_PREFIX` | `playground-workspace-init` | 所有托管区块和话题标记的命名空间。 |
| `LOCK_NAME` | `.playground-workspace-init.lock` | 工作区级排他锁文件名。 |
| `TOPIC_PATTERN` | `^\\d{4}-\\d{2}-\\d{2}-.+` | 筛选可能的话题目录名；调用时使用完整匹配。 |
| `TOPIC_MARKER_PATTERN` | topic 标记正则 | 识别 README 中带任意非空版本值的话题标记。 |

需要注意：索引扫描只检查名称形状，不校验日期是否真实存在。例如 `2026-99-99-example` 仍可通过名称正则；正常话题由 `create-topic` 生成，因此会使用有效日期。只有同时带话题标记的目录才会被收录，这可避免单凭名称认领外部目录。

## 托管内容模型

当前规范版本为 `1`。全局文档中的 Skill 内容使用带版本的 HTML 注释标记：

```markdown
<!-- playground-workspace-init:<block>:start version="1" -->
受管内容
<!-- playground-workspace-init:<block>:end -->
```

使用的区块名称为：

| 目标文件 | 托管区块 |
| --- | --- |
| 根 `AGENTS.md` | `rules` |
| 根 `README.md` | `overview`、`topic-index` |
| `workspace-management/README.md` | `workspace-management` |

话题 `README.md` 使用单行标记：

```markdown
<!-- playground-workspace-init:topic version="1" -->
```

升级时只替换已识别的托管区块，区块之外的文本保持原样。脚本检测到同一区块重复时会报错，不尝试猜测哪一个有效。已有文件完全没有相关托管区块时，脚本返回“需要语义合并”并保证本次初始化没有写入。

托管区块识别允许版本号变化，但区块名称和起止标记格式必须匹配。升级逻辑用当前模板中的完整区块替换旧区块，因此旧版本内部的手工修改也会被覆盖；用户自定义内容应放在托管区块之外。

对于一个要求多个区块的文件，只要至少存在一个要求的区块，预检就认为它已进入托管状态；随后更新逻辑会替换已有区块并追加缺失区块。例如根 `README.md` 只有 `overview` 而缺少 `topic-index` 时，初始化会保留现有文档并补上索引区块。

## 核心函数职责

| 函数 | 职责与重要行为 |
| --- | --- |
| `asset_path` / `read_asset` | 从脚本所在 Skill 根目录解析并读取模板，不依赖当前工作目录。 |
| `normalize_newlines` | 将 CRLF 和 CR 统一为 LF。 |
| `atomic_write` | 在目标旁写入带进程号的临时文件，再以 `os.replace` 原子替换；最终清理残留临时文件。 |
| `block_pattern` | 为指定区块名生成跨行、非贪婪的托管区块正则。 |
| `extract_block` | 从模板提取完整区块；模板缺少要求区块时抛出运行错误。 |
| `contains_block` / `block_count` | 判断区块是否存在并检测重复。 |
| `merge_blocks` | 按要求顺序替换现有区块或把缺失区块追加到文档末尾。 |
| `render_topic_index` | 扫描直接子目录、筛选带话题标记的 README、排序并生成 Markdown 链接。 |
| `render_workspace_readme` | 把生成的索引替换到根 README 模板中的 `{{TOPIC_INDEX}}`。 |
| `preflight_managed_file` | 在写入前校验对象类型、重复区块和完全无标记文件。 |
| `update_managed_file` | 创建新文档，或只合并指定托管区块，并返回操作状态。 |
| `workspace_lock` | 通过排他创建锁文件串行化受管文档写入。 |
| `require_workspace` | 展开用户目录、解析绝对路径并验证目标存在、为目录且不等于 Skill 根。 |
| `init_workspace` | 对三个受管目标执行全量预检，再在锁内创建或更新文件。 |
| `assert_initialized` | 验证根 AGENTS 的 `rules` 和根 README 的 `topic-index` 存在。 |
| `refresh_index` | 在锁内重新渲染根 README 的概述和索引区块。 |
| `valid_date` | 严格解析 `YYYY-MM-DD` 参数并拒绝无效日期。 |
| `create_topic` | 原子竞争目录名、渲染话题 README、刷新索引，并在失败时回滚本轮目录。 |
| `build_parser` / `main` | 定义 CLI、分发子命令、统一转换可预期异常为退出码 `1`。 |

## 命令接口

开发和诊断时可直接调用脚本。正常使用应由 `SKILL.md` 所述流程驱动，以确保语义判断和冲突处理不会被绕过。

### 初始化或升级

```text
python <skill-directory>/scripts/init_workspace.py init <workspace-root>
```

执行顺序：

1. 校验目标工作区和三个受管文档的对象类型。
2. 预检所有已有文档，检测无标记文件和重复区块。
3. 若任一文件需要语义合并，返回退出码 `2`，且不修改任何文件。
4. 获取工作区锁，创建缺失文件并更新已有托管区块。
5. 输出每个文件的 `created`、`updated` 或 `unchanged` 状态及规范版本。

初始化的全量预检发生在获取锁之前，写入发生在锁内。预检确保“无标记文件”不会导致部分写入；锁则防止遵循本脚本的并发写操作同时提交。由于预检与加锁之间存在时间窗口，外部程序仍可能在二者之间修改文件，这属于当前实现的协作边界。

初始化处理的目标固定为：

```text
<workspace>/AGENTS.md
<workspace>/README.md
<workspace>/workspace-management/README.md
```

如果 `workspace-management/` 不存在，更新该目录中的 README 时会连同父目录一起创建。如果该路径已存在但不是目录，则初始化在任何写入前失败。

### 创建话题

```text
python <skill-directory>/scripts/init_workspace.py create-topic <workspace-root> [--date YYYY-MM-DD] [--conversation-id <id>]
```

该命令要求工作区已经初始化。它使用本地时区生成创建时间，原子尝试创建 `YYYY-MM-DD-undetermined-topic[-N]/`，写入话题 `README.md`，然后刷新根索引。`--date` 主要用于可控验证；正常运行时省略即可。

如果写入 README 或刷新索引失败，脚本会回滚本次新建的空话题目录和 README，不影响既有话题。

目录分配算法从无后缀名称开始：

```text
YYYY-MM-DD-undetermined-topic
YYYY-MM-DD-undetermined-topic-2
YYYY-MM-DD-undetermined-topic-3
...
```

每次直接调用 `mkdir()`，捕获 `FileExistsError` 后递增序号。这使多个进程即使同时选择相同基础名称，也只有一个进程能成功创建该目录，其余进程会继续尝试下一个序号。

创建目录本身不使用工作区锁，避免把唯一性建立在锁状态上；索引刷新仍使用工作区锁。若两个话题并发创建，最终每个目录都唯一，但索引刷新结果仍取决于刷新时已经可见并带标记的目录。每次刷新会重新扫描全部受管话题，不做增量追加，因此后续任一刷新都能收敛到完整索引。

### 刷新话题索引

```text
python <skill-directory>/scripts/init_workspace.py refresh-index <workspace-root>
```

该命令扫描目标工作区的直接子目录，只收录同时满足以下条件的目录：

- 名称匹配 `YYYY-MM-DD-*`；
- 包含普通文件 `README.md`；
- README 含 `playground-workspace-init:topic` 版本标记。

索引按目录名排序，并只更新根 `README.md` 的 `overview` 和 `topic-index` 托管区块。

无受管话题时，索引正文为：

```text
No topic directories yet.
```

存在话题时，每行格式为：

```markdown
- [<directory-name>](<directory-name>/)
```

扫描范围仅为工作区的直接子目录，不递归查找嵌套话题。目录名直接用于 Markdown 链接，因为由正常流程创建和重命名的名称应为路径安全的日期前缀加 kebab-case。

## 初始化状态机

从系统角度，工作区可以处于以下状态：

| 状态 | 判定特征 | 允许的下一步 |
| --- | --- | --- |
| 未初始化 | 根规则或索引托管区块缺失 | 执行 `init`，必要时先语义合并。 |
| 待语义接入 | 受管目标文件存在但完全无标记 | 模型最小合并，然后重跑 `init`。 |
| 已初始化 | 根 `rules` 和 `topic-index` 区块存在 | 创建话题、刷新索引或再次升级。 |
| 部分托管 | 多区块文件只包含部分要求区块 | `init` 自动补齐缺失区块。 |
| 结构冲突 | 目标对象类型错误或区块重复 | 人工确认并最小修复后重试。 |
| 当前版本 | 所有模板区块与生成索引一致 | 重跑操作返回 `unchanged`。 |

`assert_initialized` 只检查创建话题和刷新索引所需的两个关键区块，不检查 `workspace-management/README.md`。完整规范一致性仍由 `init` 和最终人工/模型验证负责。

## 并发、原子性与幂等

- 文档通过同目录临时文件写入，再使用原子替换提交，降低中断造成半写文件的风险。
- 初始化和索引更新使用目标根目录下的 `.playground-workspace-init.lock` 排他锁。
- 等待锁的默认超时为 10 秒；锁文件超过 60 秒视为陈旧锁并清理。
- 话题目录通过直接尝试 `mkdir` 分配名称，冲突后递增序号重试，不采用先检查后创建的竞态流程。
- 相同规范版本重复执行时，已符合模板的受管文件保持 `unchanged`，不会重复插入区块。

锁只保护使用该脚本的工作区管理操作，不能阻止外部程序绕过脚本直接修改同一文件。

锁的具体流程为：

1. 以 `O_CREAT | O_EXCL | O_WRONLY` 尝试创建锁文件。
2. 成功后写入当前进程 ID 和 Unix 时间戳，便于诊断。
3. 已存在时检查文件修改时间；超过 60 秒则视为陈旧锁，删除后重试。
4. 未陈旧时每 50 毫秒重试，最多等待 10 秒。
5. 离开临界区时关闭文件描述符并删除锁文件。

陈旧判断基于文件修改时间，不会检查记录的进程是否仍存活。长于 60 秒的合法临界区可能被另一进程视为陈旧；当前三个受管文件的更新通常很短，但这是维护者在扩展脚本时必须保留意识的限制。

`atomic_write` 的临时文件名形如 `.<name>.<pid>.tmp`，位于目标文件同一目录，从而使 `os.replace` 尽量保持同文件系统内的原子语义。它保证单个文件不会以半截文本出现，但多个目标文件的更新不是跨文件事务：进程可能在更新第一个文件后中断。幂等重跑负责补齐剩余文件。

## 错误与退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 操作成功，包括没有内容变化的幂等执行。 |
| `1` | 目标无效、对象类型错误、工作区未初始化、重复托管区块、锁超时或文件系统/编码错误。 |
| `2` | 初始化预检发现无托管标记的既有文档，需要模型先做语义合并；本次没有修改文件。 |

脚本将错误写入标准错误，将成功操作结果写入标准输出。

`main` 捕获 `OSError`、`RuntimeError` 和 `UnicodeError`，把异常转换为单行 `error: ...` 并返回 `1`。参数解析错误（例如无效 `--date`）由 `argparse` 负责显示用法并返回其标准非零退出码，通常为 `2`；这与脚本主动用退出码 `2` 表示“需要语义合并”在数值上相同，但可通过输出内容区分。

初始化专用的退出码 `2` 由 `init_workspace` 直接返回，其标准错误输出包括所有需要语义合并的路径和 `No files were changed.`。这个承诺只针对该次 `init` 的预检分支。

## 模型负责的操作

下列操作不能仅凭脚本自动完成：

- 识别用户实际希望管理的工作区根目录；
- 判断无标记既有文档中的规则是否与模板等价、互补或冲突；
- 确认一个既有日期目录是否确实属于 Playground 话题；
- 根据上下文定位续接对话的原话题目录；
- 确认当前对话对目录具有重命名权，并将明确主题转换为简短英文 kebab-case；
- 在冲突或归属不确定时停止写入并向用户确认。

这一区分是系统的安全边界：脚本处理机械事实，模型处理需要理解用户意图和内容含义的决策。

## 无标记文档的语义合并协议

当脚本报告需要语义合并时，模型应：

1. 读取现有目标文件全文。
2. 读取该文件对应的 `assets/` 模板。
3. 区分用户自定义内容、旧 Playground 规则、与新规则等价的表述以及实质冲突。
4. 原样保留用户内容和无关规则。
5. 仅把明确等价或可兼容的旧 Playground 规则替换或整合为当前托管区块。
6. 避免同时保留两套含义重复的规则。
7. 若新旧规则在归属、文件移动、删除权限、Git 行为等方面冲突，先列出差异和最小选项，等待用户决定。
8. 完成合并后重跑 `init`，由脚本统一校验和更新。

脚本不得扩展为通过关键词自动判断无标记文档的含义。那会把需要上下文的所有权与权限判断退化为不可靠的字符串处理。

## 话题目录生命周期

```text
新对话开始具体任务
        |
        v
create-topic 原子创建 undetermined-topic
        |
        v
模型维护 README、在子目录中生成产物
        |
        +---- 用户未明确命名 ----> 保持原目录，只更新 README
        |
        `---- 用户明确命名 ----> 确认归属后重命名
                                      |
                                      v
                              refresh-index
                                      |
                                      v
                          后续同一对话继续复用
```

删除话题不属于脚本提供的命令。即使用户明确授权删除，执行后仍需刷新索引。工作区规则明确指出删除需要单独授权，不能作为初始化、升级或“清理”动作的隐含部分。

## 不变量与限制

- 初始化不创建 Git 仓库，也不执行暂存、提交、分支切换、重置或推送。
- 系统不为符合规范而主动删除、迁移、认领或重命名既有内容。
- 既有项目文件保留在原路径。
- 纯初始化、升级和维护只使用 `workspace-management/`。
- 一个新对话创建一个新话题目录；一个续接对话复用其原目录。
- 根索引只表示带有效话题标记的受管目录，不代表所有日期命名目录。
- 当前实现没有自动话题重命名命令；重命名由模型在确认归属后完成，再调用 `refresh-index`。

## 已知实现限制

- 规范版本是脚本常量和模板标记的约定，没有独立迁移注册表；新版本升级逻辑需要同步更新模板、脚本和文档。
- 脚本拒绝的只有与 `SKILL_ROOT` 完全相同的目标路径，不会判断其父目录或子目录是否适合做工作区；正确目标选择仍由模型负责。
- `refresh-index` 会同时更新 `overview` 与 `topic-index`，因此概述区块中的手工修改会被模板覆盖。
- 话题标记正则接受任意非空版本值；旧版本话题仍会进入索引。
- 索引目录名正则验证格式而不验证真实日期，也不验证英文 kebab-case。
- `create-topic` 的失败回滚假设本轮目录中只有本脚本写入的 README；脚本创建到回滚之间若有外部程序加入文件，`rmdir` 会失败并向上报告。
- 创建话题目录与刷新索引不是单一事务。目录和 README 已成功但索引更新失败时，回滚会尝试移除本轮创建内容；外部并发写入可能影响回滚。
- 多文件初始化不是事务性提交，中断后依赖幂等重跑恢复一致状态。
- 锁协调的范围仅限使用相同锁约定的进程，不能保护用户编辑器或其他工具的直接写入。
- 脚本不提供只读 `check` 子命令。只读检查需由模型读取文件完成，不能运行会写入的 `init` 代替。

这些限制不必通过增加复杂抽象立即消除；维护时应根据真实故障和需求做最小修正。

## 安全审查要点

维护或扩展脚本时，需要保持以下不变量：

- 不以目录名相似作为对话归属证明；
- 不对无标记文档执行盲目覆盖或字符串猜测合并；
- 不在初始化过程中移动、重命名或删除既有内容；
- 不加入自动 Git 初始化、暂存、提交、切换、重置或推送；
- 不让升级写入托管区块之外的用户文本；
- 不把普通任务产物写入 Skill 安装目录或工作区根目录；
- 不因索引缺失而自动给所有日期目录加话题标记；
- 任何新增删除或迁移能力都必须有与影响相称的显式授权和停止条件。

## 验证建议

修改实际 Skill 后，至少执行：

```text
python -m py_compile <skill-directory>/scripts/init_workspace.py
python <skill-creator-directory>/scripts/quick_validate.py <skill-directory>
```

行为验证应在临时工作区进行，覆盖空目录初始化、无标记文件预检、重复初始化、并发创建话题、索引刷新和失败回滚。不要在 Skill 安装目录或真实用户工程中直接做破坏性测试。

推荐的最小验收矩阵如下：

| 场景 | 操作 | 预期结果 |
| --- | --- | --- |
| 空工作区 | `init` | 创建三个受管文档，版本为 1，不创建日期话题。 |
| 重复初始化 | 连续两次 `init` | 第二次全部为 `unchanged`，没有重复区块。 |
| 无标记根文档 | 预置普通 `README.md` 后执行 `init` | 退出码 2，列出路径，本轮无文件变化。 |
| 多个无标记文档 | 预置普通 AGENTS 和 README | 一次列出所有待合并路径，本轮无部分写入。 |
| 重复区块 | 在一个文件复制同名区块 | 退出码 1，不自动选择或删除区块。 |
| 部分托管 README | 只保留 `overview` 后执行 `init` | 保留区块外内容并补上 `topic-index`。 |
| 对象类型冲突 | 创建名为 `workspace-management` 的普通文件 | 初始化失败，不覆盖该对象。 |
| 首个话题 | `create-topic` | 创建无后缀目录、写 README、根索引新增链接。 |
| 同日多个话题 | 重复或并发 `create-topic` | 每个目录名唯一，使用最小可用序号。 |
| 无效日期参数 | 使用不存在的日期 | 参数解析失败，不创建目录。 |
| 未初始化创建话题 | 缺失根规则或索引时执行 `create-topic` | 退出码 1，不创建话题。 |
| 索引过滤 | 混入无标记日期目录 | 只收录 README 带有效话题标记的目录。 |
| 空索引 | 没有受管话题时 `refresh-index` | 索引显示 `No topic directories yet.`。 |
| 话题重命名 | 模型确认归属并重命名，再刷新索引 | 旧链接消失，新链接出现，目录内容保持不变。 |
| 写入中断 | 在部分文件更新后重跑 `init` | 已完成部分保持稳定，缺失部分被补齐。 |
| 用户区块外内容 | 在受管文件区块外添加文本后升级 | 自定义文本原样保留。 |

验证完成后还应运行 `quick_validate.py`，检查 Skill 名称、frontmatter、目录结构和未完成占位符。该验证器不能证明工作区所有权判断或语义合并正确，因此不能替代上述行为测试与人工审查。

## 版本升级维护流程

发布后续规范版本时，维护者至少需要：

1. 明确新版本改变了哪些受管行为，避免把与当前需求无关的规则加入模板。
2. 更新相关 `assets/` 模板中的版本标记和受管内容。
3. 更新脚本 `VERSION`，并确认区块正则仍能识别旧版本。
4. 检查 `SKILL.md` 的流程、约束和实际命令是否仍与脚本一致。
5. 更新本目录 `SPEC.md`、使用说明和系统说明中的版本或行为描述。
6. 使用旧版受管文件做升级测试，确认区块外内容原样保留。
7. 验证重复升级幂等、缺失区块可补齐、重复区块仍拒绝自动处理。
8. 运行语法检查、行为矩阵和 `quick_validate.py`。

版本升级不应顺带迁移旧话题目录名称。目录归属和重命名仍遵循明确用户指令与当前对话所有权判断。
