# playground-workspace-init 使用说明

## 用途

`playground-workspace-init` 用于初始化或安全升级一个短会话、多主题并存的 Playground 工作区。它为每个具体对话分配独立的话题目录，并通过根目录规则和话题说明保存归属与上下文，避免不同对话的文件、脚本、依赖和中间产物相互混淆。

它适合临时研究、资料整理、工具试验和短期脚本，不适合生成正式项目结构、整理既有源码或管理 Git 分支与提交。

## 适用范围

适合使用本 Skill 的情况包括：

- 一个工作区会被多个彼此独立的 Codex 对话反复使用；
- 每个对话的产物生命周期较短，但仍需要保留足够信息以便后续继续；
- 希望把一次性脚本、下载文件、实验依赖和中间结果限制在各自话题目录中；
- 工作区已经存在一些内容，需要在不接管这些内容的前提下引入统一规范；
- 已经使用旧版 Playground 规范，需要升级 Skill 管理的规则和索引区块。

不适合使用本 Skill 的情况包括：

- 为 IDE、构建系统或产品仓库搭建正式工程骨架；
- 自动整理或重构已有项目的源码布局；
- 把多个已有目录自动判断为某次对话的产物；
- 自动初始化或维护 Git 仓库、分支、提交和远程仓库；
- 仅需处理一个具体任务，且目标工作区并不是多主题 Playground。

## 核心概念

系统区分三类内容：

| 类型 | 位置 | 归属与用途 |
| --- | --- | --- |
| 全局规则 | 根 `AGENTS.md`、根 `README.md` | 对整个 Playground 生效，保存工作区规则与话题索引。 |
| 工作区管理 | `workspace-management/` | 仅用于初始化、升级、检查和维护规范，不属于具体业务话题。 |
| 具体话题 | `YYYY-MM-DD-topic[-N]/` | 由一个对话拥有，保存该对话生成的文件、工具和上下文说明。 |

“一个目录由一个对话拥有”是最重要的隔离规则。新对话不能因为目录名称相似就认领已有目录；续接对话也不能因为再次打开或多轮运行就重复创建目录。

## 使用前准备

调用前需要确认：

1. 当前打开的目录就是希望初始化或升级的目标工作区。
2. 如果用户在请求中指定了其他目录，应明确使用那个目录，不能误把 Skill 安装目录作为目标。
3. 对目标目录具有读取权限；需要创建或更新规则时还需写入权限。
4. 对于已有工作区，重要内容应保持现状。Skill 会检查 Git 状态（若适用），但不会借此执行任何 Git 写操作。

目标根目录必须已经存在。Skill 负责在其中创建规范文件和目录，不负责创建目标工作区本身。

## 调用方式

该 Skill 关闭了隐式调用，必须由用户明确选择或提及。安装 Skill 后，在目标工作区中使用：

```text
$playground-workspace-init 初始化当前多主题工作区，保持现有内容不变。
```

升级已有 Playground 工作区时使用：

```text
$playground-workspace-init 将当前 Playground 工作区升级到最新版规范，保留已有文件、目录和用户规则。
```

初始化、升级和纯工作区维护操作使用固定的 `workspace-management/`，不会为这类操作额外创建日期话题目录。

还可以用更明确的请求约束范围：

```text
$playground-workspace-init 检查并初始化当前工作区。不要移动、重命名或删除任何已有内容；如有规则冲突，先列出冲突并询问我。
```

```text
$playground-workspace-init 只检查当前 Playground 是否符合最新版规范，说明需要修改的内容，暂时不要改文件。
```

第二种请求是只读检查。Skill 的正常初始化流程允许写入，但用户明确要求只检查时，应遵守更窄的授权范围。

## 初始化流程

一次完整初始化或升级按以下顺序进行：

1. 确认目标工作区根目录，避免把 Skill 自身目录或其他无关目录作为目标。
2. 查看根目录现状、`AGENTS.md`、`README.md`、`workspace-management/README.md`，并在适用时查看 Git 状态。
3. 判断当前状态是空工作区首次初始化、无标记旧工作区首次接入、已有受管工作区升级，还是已经符合当前版本。
4. 运行初始化脚本的预检。只要任一同名已有文档完全没有托管区块，本轮脚本就不写入任何文件。
5. 对无标记文档进行最小语义合并。保留用户内容，只把明确等价的 Playground 规则纳入托管区块。
6. 遇到实质冲突或无法确认含义的内容时停止相关写入，说明冲突与最小处理选项，等待用户确认。
7. 重新运行初始化脚本，创建缺失文件并升级已识别的托管区块。
8. 仅在上下文明确证明某个既有日期目录是旧 Playground 话题时，为其 README 添加话题标记；不能仅凭名称推断。
9. 刷新话题索引，检查必要文件可读、托管区块不重复、用户内容仍被保留。
10. 汇报实际新增、更新、保留和未解决冲突。

## 初始化结果

首次初始化空工作区后，根目录至少包含：

```text
<workspace>/
|-- AGENTS.md
|-- README.md
`-- workspace-management/
    `-- README.md
```

- `AGENTS.md`：约束后续对话的话题归属、文件放置和完成前检查。
- `README.md`：说明工作区用途并维护话题索引。
- `workspace-management/README.md`：记录工作区规范版本与维护状态。

已有内容不会因初始化而被主动移动、重命名或删除。已有 `AGENTS.md`、`README.md` 或 `workspace-management/README.md` 没有托管标记时，Skill 会先读取并进行最小语义合并；存在实质冲突时会保留原内容并请求确认。

初始化不会预先创建空的话题目录、`scripts/` 或 `tools/`。这些目录只在具体任务确实需要时创建。

## 初始化状态判定

| 现状 | 处理方式 |
| --- | --- |
| 三个受管文档均不存在 | 直接从模板创建，并建立 `workspace-management/`。 |
| 同名文档已存在且含托管区块 | 保留区块外内容，只更新或补齐对应托管区块。 |
| 同名文档已存在但完全没有托管区块 | 所有初始化写入暂停，由模型先做最小语义合并。 |
| 同一托管区块出现多次 | 报错并停止，不能自动选择保留哪一份。 |
| `workspace-management` 已存在但不是目录 | 报错并停止，不覆盖该对象。 |
| 已符合当前版本 | 文件保持不变，结果报告为 `unchanged`。 |

“最小语义合并”并不等同于把模板直接追加到文件末尾。模型需要先识别已有内容中是否存在相同规则，避免形成重复或相互矛盾的说明。

## 开始新话题

具体任务开始前，新对话会创建独立目录：

```text
YYYY-MM-DD-undetermined-topic/
`-- README.md
```

同名目录已存在时，目录名依次使用 `-2`、`-3` 等最小可用序号。新对话不会认领或复用已有话题目录；续接旧对话则根据对话上下文和话题 `README.md` 复用原目录。无法确认归属时，Skill 会在写入前询问用户。

例如同一天连续创建三个话题时，初始目录可以是：

```text
2026-09-17-undetermined-topic/
2026-09-17-undetermined-topic-2/
2026-09-17-undetermined-topic-3/
```

序号只用于解决名称冲突，不表达优先级或话题之间的关系。创建日期采用执行环境的本地日期。

话题 README 初始记录以下信息：

| 字段 | 含义 |
| --- | --- |
| Created date | 本地创建日期。 |
| Created time | 带时区偏移的创建时间。 |
| Conversation or task ID | 可用时记录对话或任务标识；不可用时写 `Unavailable`。 |
| Initial directory | 首次创建的目录名，即使后续重命名也可用于追踪。 |
| Current topic | 当前话题，创建时为 `Undetermined`。 |
| Purpose | 当前对话目标或用途。 |
| Main files and outputs | 主要文件与最终产物。 |
| Status | 当前执行状态。 |
| Pending work | 尚未处理或需后续完成的事项。 |
| Continuation entry point | 恢复该话题时应先查看的内容和下一步。 |

对话进行中不需要为每条消息更新 README，但产物、状态或未处理事项发生变化后，应在任务结束前同步更新。

## 续接旧话题

重新打开同一对话、继续发送消息或让同一对话执行多轮，都属于续接，不会创建新目录。定位原目录时应依次参考：

1. 当前对话上下文中已使用的绝对或相对路径；
2. 话题 README 中的对话或任务标识；
3. 初始目录、创建时间、当前话题、主要文件和续接入口；
4. 根 README 的话题索引。

相同日期、相近名称或相似文件本身不足以证明归属。如果仍有两个以上合理候选目录，必须先询问用户，不能试写文件来“验证”归属。

明确指定话题后，例如：

```text
将该对话主题定为串口日志分析。
```

Skill 会把当前对话自己的目录改为简短的英文 kebab-case 名称，例如 `YYYY-MM-DD-serial-log-analysis/`，并同步更新话题说明和根话题索引。普通任务内容变化不会自动触发重命名。

重命名遵循以下规则：

- 仅在用户明确指定主题或明确要求重命名时执行；
- 只重命名当前对话已确认拥有的目录；
- 保留最初的日期前缀和目录中的全部内容；
- 英文主题只使用便于路径使用的简短 kebab-case；
- 目标目录已存在时追加最小可用数字后缀；
- 更新话题 README 的当前话题和相关状态，但保留 `Initial directory` 作为追踪信息；
- 重命名完成后刷新根 README 的话题索引。

当前脚本没有提供自动重命名命令。重命名由模型在确认归属和目标名称后执行，再调用索引刷新命令。

## 文件放置

- 当前对话新建、复制、下载或生成的文件放在当前话题目录中。
- 单文件或一次性脚本放在 `scripts/`。
- 多文件工具放在 `tools/<tool-name>/`，依赖和配置随对应工具存放。
- 只创建当前任务需要的子目录，不预建空目录。
- 既有项目文件继续在原路径修改，不为归档而搬入话题目录。
- 工作区外原始资料默认只读，需要副本时复制到当前话题目录。

以下例子展示推荐布局，而不是要求预先创建所有目录：

```text
2026-09-17-serial-log-analysis/
|-- README.md
|-- inputs/
|   `-- captured-log.txt
|-- scripts/
|   `-- summarize_log.py
|-- tools/
|   `-- decoder/
|       |-- decoder.py
|       `-- requirements.txt
`-- results/
    `-- summary.md
```

如果当前任务只生成一个结果文件，则无需为了形式创建 `inputs/`、`scripts/`、`tools/` 或 `results/`。用户明确指定为跨话题共享的内容可以保留在根目录，但这种例外需要明确意图，不能由模型自行推断。

任务结束前，Skill 会更新当前话题 `README.md` 中的当前话题、目标、主要产物、状态、未处理事项和续接入口，并检查根话题索引是否与真实目录一致。

## 安全边界

在初始化、升级和目录管理过程中，该 Skill 不会：

- 删除文件或覆盖用户未提交的修改；
- 移动归属不明或属于其他话题的内容；
- 主动初始化 Git，或执行暂存、提交、切换分支、重置和推送；
- 停止正在运行的服务或工具；
- 为符合新规范而自动迁移、重命名既有目录。

这些限制只约束工作区管理操作，不限制用户在具体任务中明确授权的正常文件或进程操作。

如果移动当前话题文件可能破坏路径引用、依赖关系或正在运行的程序，应保持文件原位，并把例外及原因记录到话题 README。工作区规范不应为了目录整齐而破坏可运行状态。

## 升级规则

规范升级以托管区块为单位，不整份覆盖文档：

1. 识别现有托管区块及其版本。
2. 用当前 Skill 模板替换对应区块。
3. 保留区块之前、之后以及其他不相关区块中的用户内容。
4. 缺失但可安全添加的受管区块会被补齐。
5. 无标记文件由模型做一次语义接入，脚本不根据关键词猜测。
6. 旧话题目录不因新版命名规则而自动迁移或改名。
7. 升级后重新计算索引并检查重复区块。

因此，“升级到最新版”表示更新由 Skill 管理的规则，不表示把整个工作区改造成统一目录风格。

## 完成后的核对清单

初始化或升级完成后，应能确认：

- 根 `AGENTS.md` 中恰好有一个 `rules` 托管区块；
- 根 `README.md` 中各有一个 `overview` 和 `topic-index` 托管区块；
- `workspace-management/README.md` 中恰好有一个管理托管区块；
- 托管区块版本为当前版本，区块外用户内容仍存在；
- 根索引只列出真实且带话题标记的目录；
- 当前对话没有误用其他对话的目录；
- 初始化前已有内容没有被移动、重命名或删除；
- 当前对话产物没有无意遗留在根目录；
- 最终报告列明新增、修改、保留和未处理内容。

一个清晰的完成报告通常应包含类似信息：

```text
已创建：AGENTS.md、README.md、workspace-management/README.md
已更新：无
已保留：初始化前已有目录及文件，未移动或重命名
未解决冲突：无
规范版本：1
```

## 常见情况

### 提示需要语义合并

目标工作区已有同名文档，但没有本 Skill 的托管区块。脚本会停止且不修改任何文件，由模型读取现有内容和模板后做最小合并。若规则冲突且无法安全判断，会请用户选择。

如果有多个文件需要合并，脚本会一次列出全部路径，避免先改一部分文件后才发现另一处冲突。

### 重复初始化或升级

已经符合当前规范时，重复调用不会重复添加规则、索引或管理目录。托管区块之外的用户内容保持不变。

### 话题没有出现在根索引中

只有目录名符合日期话题格式、且其 `README.md` 含有效话题标记的目录才会进入索引。相似的既有目录不会被自动认领。

确认该目录确实属于本规范后，才可补充话题标记并刷新索引。不能为了让索引“完整”而给未知目录批量加标记。

### 恢复旧对话

先查看候选目录的 `README.md`，结合创建信息、对话或任务标识、当前状态和续接入口确认归属。若仍无法可靠确定，应在写入或移动文件前询问用户。

### 提示工作区未初始化

`create-topic` 和 `refresh-index` 都要求根 `AGENTS.md` 存在 `rules` 区块、根 `README.md` 存在 `topic-index` 区块。缺少任一项时，应先完成 `init` 流程，而不是手工绕过检查。

### 提示重复托管区块

同一文件中出现了两份或更多相同托管区块。自动替换可能误删用户选择，因此脚本会停止。应先阅读各区块和周边内容，确认应保留或合并哪一份，再进行最小修复。

### 提示等待锁超时

另一个初始化或索引刷新操作可能正在修改同一工作区。先确认是否有并发操作仍在运行，不要直接删除新鲜锁文件。脚本只会自动清理修改时间超过 60 秒的陈旧锁。

### 初始化中断

受管文档采用临时文件加原子替换写入。中断后可以重新显式调用初始化；幂等逻辑会保留已完成内容并继续补齐缺失部分。仍应检查是否存在未解决的无标记文档或重复区块。

## 用户可预期的最终结果

使用该 Skill 后，用户应得到的是一个可持续遵守的工作区约定，而不仅是几份初始文件：后续新对话会创建自己的目录，续接对话会复用原目录，任务产物有明确归属，根索引可以定位所有受管话题，且初始化前的内容不会被自动接管。若系统无法证明某项内容属于当前对话，默认行为是保持原样并询问，而不是猜测。
